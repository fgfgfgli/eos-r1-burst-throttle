## 大白话

一台 R1 的固件被解开成明文之后，可以看到它是怎么从卡上读一段程序、怎么在内存里改自己的代码、怎么决定"这一帧要不要拍"、以及 6K 视频为什么只能录 17:9。

这个项目把这些路径一条条摸清楚，并在**据研究记录为研究者自有的相机**上验证了其中一部分（**设备归属仍待作者确认**，见 [DISCLAIMER.md](DISCLAIMER.md) §5）：连拍快满的时候不要死等，而是主动降速再继续；在**相机已被设成从卡启动**的前提下，开机就自动打上补丁，不插 USB 也能生效。

6K 全高（OpenGate）**还没做成**——现在知道它死在副核（Radon）的一条断言上，这是本轮最接近根因的结论，但不是"已打通"。

### 逐项说明

#### 1. 固件与静态分析 `[V]`

R1 的更新包（FIR）按 AES-128-CTR 分段封装（**仅记到这一层**）；解开后主 AArch64 段载入 `0xE0500000`，文件偏移与虚拟地址是固定的线性关系：

```
file_offset = VA − 0xE0500000 + 0x000CC7C0
```

六版固件全部解出，18 个部件的明文校验和逐个通过；同平台机型（材料里记作 R5M2 / R52）1.3.2 走同一路径解出，作为阳性对照。

**本仓库不复述密钥材料、容器细节或解密脚本。** 需要复核的读者请自备合法持有的固件；也请注意：**能否做这一步，取决于你所在法域**（见 [DISCLAIMER.md](DISCLAIMER.md) §4）。

#### 2. USB 工厂通道 `[V]`

相机通过 WPD/MTP 暴露一套厂商扩展接口（R1：`VID_04A9 / PID_3313`），握手后可以**按名字**调用固件内部命令表里的处理函数。其中两个处理函数的全部实现就是一条 `ldr` 和一条 `str`：读一个 32 位字、写一个 32 位字。

⇒ 一台量产的、未改机的相机，在这个会话里可以被任意读写 4 GB 地址空间。

> ⚠️ 这两个处理函数**没有任何对齐、范围或只读检查**。写一个未映射地址会让 PTP 任务直接卡死（相机界面还在，但 USB 不再响应，需要断电）。这是本项目的第二次教训：能力越大，越要先想清楚"写错了怎么办"。

细节见 [docs/03](docs/03-usb-factory-channel.md)。

#### 3. 页表重映射 `[V]`

固件镜像区（`0xE0500000`–`0xE2F00000`）在 **MMU 层是可写的**（AP=00，EL1 RW），但**介质层看起来是只读的 ROM 镜像窗口**：直接 `str` 会停在 write-back D-cache 里，回读立刻是新值，几分钟后（或 cache 被刷掉后）回退原值。

> "介质只读"这个解释是 `[I]`（强），不是排他证明——反面证据与残余不确定性写在 [docs/04](docs/04-mmu-and-remap.md) §2。

所以"直接 Poke 几条指令"不是补丁方案。真正的做法是：

1. 在 RAM 里建若干 L3 页表（512 项，默认恒等映射）；
2. 把目标 ROM 页拷到 RAM 副本上，在副本里改；
3. 把 L2 的 2 MB block 描述符换成指向 L3 的 table 描述符；
4. 做架构要求的 cache 与 TLB 维护（改了代码就必须让取指路径看到新字节）。

此后 CPU 取到的就是我们改过的页。**全程 RAM-only：断电即回原厂。** 机制与证据等级见 [docs/04](docs/04-mmu-and-remap.md)。

#### 4. 卡启动（BootDisk + AUTOEXEC）`[V]`，有前提

卡上写 exFAT 启动标记（主启动扇区 + 备份启动扇区两个副本，改完都要按 exFAT 规范重算启动区校验和），根目录放两个平坦二进制载荷：`AUTOEXEC.bin`（AArch64，载入 `0x09000000`）与 `S1_AUTOEXEC.bin`（Thumb，载入 `0x00800000`）。

> 标记的具体偏移、标记字符串在扇区内的位置、校验和算法细节与存放位置、受影响的扇区数、备份方式，全部不在公开版（内部记录里）。

**A/B 对照（同卡同载荷，只切机身的 BootDisk 标志）：**

| 组 | BootDisk | 结果 |
|---|---|---|
| A | 关 | 正常开机 |
| B | 开 | **完全没反应**（长时间不亮灯） |

**能下的结论**：BootDisk 标志确实门控了一条"读取并执行卡上代码"的路径 `[V]`。
**不能下的结论**：这组对照**不能**证明"B 组的卡上代码跑了"——它只说明相机停在了某处。另一解释（标志打开后相机去读卡，而这批自制卡读取失败导致挂起）当时**没有完全排除** `[?]`。

**旁证**：safe 载荷（立即跳回原厂入口）在标志开时**正常开机** ⇒ 加载器能读卡、能跳转；hang 载荷（死循环）在标志开时 → Err02/卡死，需取电池。这是**强旁证**，但不是"控制流必然转移到卡上代码"的排他性逻辑证明。

**载荷能否改写主固件内存：当时尚未定论 `[?]`**，后来绕开了这条路。

**后来（同日 19:5x）冷启动驻留桥实机通过 `[V]`**——但请注意前提：

> **前提**：BootDisk **此前已被开启**，卡上标记与载荷已准备。
> **结论**：在这个前提下，开机自动打补丁成立，全程不需要 USB。
> **未证明**：出厂默认状态下"零持久写"的目标。BootDisk 是可逆的持久状态，**可逆不等于不存在**。

做法是不去写固件区，而是**接管复位片段**：把复位代码搬到 RAM 执行，在它调用 cache 清洗例程的那一处挂一个 wrapper，wrapper 现场生成 L3 表、拷页副本、写跳板、改 L2 条目，然后 tail-branch 回原厂流程 ⇒ **MMU 一打开就已经带着补丁**。开机后只用 USB 只读回读复核：页表项、跳板首字、L3 恒等项、重试常量全部与预期一致；连拍实测不崩、降速生效。

> ⚠️ 这一段有四个必须记住的教训（详见 [docs/02](docs/02-cardboot.md) §5.4）：坏卡会让"同一载荷时好时坏"；EL3 安全态下写非安全 DRAM 不可靠；wrapper 必须 tail-branch 而不是 `blr` 后 `br`；低区载入地址开机后会被清零，持久数据要放页表空洞里。
>
> **关闭方式**：卡上删掉 `AUTOEXEC.bin` **并且**清掉启动标记。只删文件而标记还在 = Err02。

#### 5. FAEXE 路径 `[V]`

比卡启动更"温和"的一条路：工厂命令 `InitializeAdjustmentSystem` 的加载器会去读**卡根** `A:/faexe.bin`（再试 `B:/faexe.bin`），或者读经 USB 上传到程序区（约 1 MB 可执行 RAM）的模块；解码后 `blr` 到偏移 0 执行，跑完再从程序区末尾的固定槽取出回调地址并调用它（**回调的参数不是那个槽**，见 [docs/03](docs/03-usb-factory-channel.md) §3.2）。

实机确认两件事：

- USB 路线（分配 → 上传 → 执行）返回的回调值与我们的代码一致，阴性/阳性对照都对上 `[V]`；
- **卡根 `faexe.bin` 被读取、解码、执行**，回调返回值原样传回 `[V]`。

**限制（带条件说）**：

- 触发者是工厂命名命令，**不是冷启动自动执行** `[V]`；
- 初始化位一旦置位（= 上次回调返回偶数），后续调用立即返回、不再执行新上传的字节 `[V]`；反之（回调返回奇数）**可以反复跑**，但每次都必须重新上传（解码是原地的）`[V]`+`[I]`；
- `TerminateAdjustmentSystem` 有**三条互斥分支**，结果完全不同 `[V]`：① 前置不满足（初始化位或工作区指针为 0）⇒ 返回 `0x17` **早退**，**不释放、不清位**（本次实机走的就是这条）；② 工作区释放失败 ⇒ 返回错误码、**不清位**，没走到释放程序区；③ 走到最后 ⇒ 释放工作区、**释放程序区**、**清位**，但**不注销**命名区 ⇒ 悬垂。所以"它不清标志"和"它释放程序区留悬垂"都不对——**要看分支**；
- ⇒ **最稳的复位是断电重启**，不是调 Terminate。

> 🔴 本仓库**不提供**这个模块的编解码密钥、算法常数、上传格式或任何可执行 payload。机制与 ABI 的描述见 [docs/03](docs/03-usb-factory-channel.md)，够你理解，不够你直接造一个能跑的。

#### 6. 连拍降速 / 节流 `[V]`

**先说结论：这个目标做成了（现象层面）。** 但它不是"改一个数字"就完事，中间有三轮失败。

| 轮次 | 做法 | 结果 |
|---|---|---|
| E1 | 挂起/待机重试数值 3000 → 500 ms | "停，但接上的快"——恢复变快，仍会停 |
| E2 | 同上改到 50 ms | 缓冲满瞬间 **Err70** |
| E3 | 把"配额挂起/释放结束"两处分支都改成无条件跳转 | **仍然会停** ⇒ 真正的闸不在这里 |
| v4 | 在释放请求分发点装跳板，按缓冲水位自旋延时 | 「降速 → 短暂 busy → 又继续」成立，但**自旋**是隐患 |
| v10 | 自旋硬钳位 35ms | 单次自旋 ≤35ms 不崩；40ms 崩 |
| **v14／定稿** | **不自旋**：水位低于阈值时把「继续拍」这个结论改写成「挂起」，复用相机自己的挂起路径 + 把重试数值改小 | 实机确认：拍一阵 → 停一下 → 再拍一阵，按键活动下不崩 |

关键观测：挂起瞬间**前端缓冲空位 = 3**（满容量 40）⇒ 在这组观测里，连拍的"停"是**前端缓冲写满**，不是帧数配额。配额那一条只是同一现象的另一面。

负结论（带边界）：**准入链的直接调用面里没有"卡/写卡"这个输入**。规则求值只返回 0/1/2/3/4 五个规则号，只有规则 0 会真正发起下一帧；整条链唯一的比较是帧计数。
但**多跳没有排除**：job 层完全可能把某个字段写成"卡忙"再由本链读到 `[?]`。

> ⚠️ **自旋红线**：任何自旋叠加"AF-ON 二段快速切档 + 连拍"都会偶发 Err70（15–35ms 也测到过）。这条链涉及的定时器里**没有观察到** 50–100ms 级的值（最小 2500 ms），所以**本次**把注意力放到**传感器曝光层**：`SR ExposureStartTiming is overrun`、`ExecAccumH over VdSize`、`[SLCP] AccumH is less than min-VD` 这些断言按 VD（≈1–2 帧）计时。**但具体是哪一条先触发，本轮没有捕获** `[?]`；也**不能**由此断定其它层绝对没有更短的超时。

细节、参数表与失败矩阵见 [docs/05](docs/05-burst-throttle.md)。

#### 7. AF 每秒检测次数：观测 / 机制 / 提频，三件事分开说

用页表重映射在命令发送器的唯一入口装计数桩，USB 只读回读。相机停在 **4K 视频档**、无人工操作：

| 窗口 | Δcmd7 | 时长 | cmd7 / 秒 | cap 查询 / 秒 |
|---|---|---|---|---|
| #1 | 312 | 5.206 s | **59.93** | 299.7 |
| #2 | 312 | 5.210 s | **59.88** | 300.2 |

**这只是两个 4K 窗口**。与 60 fps 的相对差约 **0.115%** 与 **0.192%**（两窗口之间约 0.077%）。

| 问题 | 答案 |
|---|---|
| 这两个窗口里每秒多少次？ | **约 59.9**，`[V]` |
| 是不是全模式都严格等于 LV 帧率？ | **不是已证事实**。只测了 4K 视频档；4K 120p / 30p / 6K 60p / 拍照伺服 AF 都**没测** `[?]` |
| 有没有独立定时器 / 软件上限？ | **只做了有界扫描**：在 DAF 命令族与 AF 决策层里没找到分频结构。**不能声称"不存在"** `[?]` |
| 机制是什么？ | `[I]`：每秒次数 ≈ min（raw 帧产出率、引擎处理率、主核同步往返率）。这是四条证据合成的模型，**无实测** |
| 能提频吗？ | **未上机** `[?]`。改行模式是"换档"不是"提频"；而且**全函数替换会把拍照档也改掉** |

**没做完的部分**：把行模式选择器改成"恒返回 2"的补丁**设计好了但没上机**。两种改法风险完全不同（全函数替换会污染拍照档；掩码只影响视频档），本稿**不宣布任何"行为不变"**。而且它与 6K 全高共用同一条读出链，两项必须一起评估。

详见 [docs/06](docs/06-af-rate.md)。

#### 8. 6K OpenGate `[V]` 现象 / `[I]` 根因 / 未成功

**先纠正一个早期的错误假设**：6K RAW 用的 cap 是 **55**，不是 54。在谓词里埋日志后，拨到视频档读到 `0x37`。

- CAP[55] = SensorMode **4** = `6208×3320`（17:9）⇒ 录出来 6000×3164，与现状完全对上；
- CAP[54] 是 SensorMode 5（`6208×6640`），不是 6K RAW 的槽。

**Err70 实验矩阵（全部 RAM-only）：**

| 补丁 | 结果 |
|---|---|
| 只重映射页表、**一个值都不改** | ✅ 正常录像（这一次对照通过） |
| CAP[55] 4→1（只改传感器模式） | 拨到视频档 **Err70** |
| CAP[55] 4→1 + 谓词对该 cap 返回 class 2 | **Err70** |
| 再加 DS 几何成套改 | **Err70**（卡得更久，说明代码走得更深） |
| CAP[54] 5→1（早期，cap 认错） | 正常录制，仍是 3164 |

⇒ 正确的说法是：**已试的这些改动都不足以让它通过**；不能说"Err70 与 class、几何无关"（那几个变量只是被"改过"，不是被"排除过"）。

**再纠正一个容易被误读的地方**：R1 里"全高/DS-2"这一层是**被桩掉的**——DS 选择器的第二个谓词就是 `mov w0,#0; ret`，永远返回 0。所以 R1 没有全高视频不是"参数没调对"，而是**这条路径在固件里被禁用** `[V]`（但这条不能单独推出"全机不存在其它全高路径"）。

**根因收窄（本项最有价值的部分）：**

1. 发现副核有**独立的运行时 CAP 副本**，此前所有实验只改了 ROM 页、没改运行时 ⇒ 之前全部跑在"不一致"状态 `[V]`；
2. 把三处都改成 1 后仍然 Err70 ⇒ **主核观测到三处一致的情况下仍失败** `[V]`。注意：这**不等于**"表一致性已被完全排除"——副核的 **cache 可见性未验证** `[?]`；
3. 装"吞断言"探针后不再 Err70，变成**黑屏但相机还活着** ⇒ 失败是一条断言 `[V]`；
4. 抓到断言点：`ImageSequence::ImageSequenceParam.c` **行 1748**，条件就是 **`a2 == 0`**；`a2` 必须落在 `1..0xFFFF`。这个校验函数有 **53 个调用者，全部落在传感器读出/DMA 配置模块** `[V]` ⇒ 它是"给传感器写一个 16 位值"的统一校验器，**失败发生在某次寄存器写入时值是 0** `[V]`；
5. 同一次状态 dump 里：`LvCapMode = 55`（证明主核确实把 55 送进去了）、**`FrameRate = 0`** `[V]`。读出驱动里大量 16 位值由"帧率/VD"派生 ⇒ **帧率 0 很可能让某个派生值变成 0** `[I]`。**这条因果没有数据流证据，不能写"根因已证"。**

**被撤回的推断**：中途曾认为副核判决函数算出了非法 SensorMode/Vsize。断电重启读同一组地址，值与故障态**完全一样** ⇒ 那些是复位默认值 `[V]`；该推断已撤回。

**当前状态**：6K OG **没有做成**。补丁全部是 RAM-only，断电即回原厂。下一步候选（让主核发给副核的 `FrameRate` 非 0 / 找到具体写 0 的寄存器调用点）都还在设计阶段。

详见 [docs/07](docs/07-open-gate-err70.md)。

## 技术要点

**架构**：DIGIC X 平台，主核 AArch64（复位时在 EL3，随后 `eret` 到 EL1h），另有一颗 **Xtensa 副核（Radon）**——视频/传感器模式判决在副核侧，主核只下发 `LvCapMode` + `FrameRate` `[V]`+`[I]`。这一条解释了为什么"只改主核表"反复无效。

**关键地址空间**（R1 1.3.0，只到"区"级）：

| 区间 | 用途 |
|---|---|
| `0xE0500000` | 主镜像 AArch64 复位入口（**不是可调用函数**，结尾 `b .`） |
| `0xE0500000`–`0xE2F00000` | 固件镜像区（MMU 可写 / 介质疑似只读） |
| `0xDFFC0000` 起 | 页表 SRAM（运行期 `TTBR0` / L2 就在这块） |
| `0xD4000000` / `0xD4080000` | Radon 代码镜像 / 数据模块（运行时装入点） |
| `0x44780000` 一带 | FAEXE 程序区（约 1 MB 可执行 RAM） |
| `0x09000000` | `AUTOEXEC.bin` 载入点（开机后被清零） |
| `0x00800000` | `S1_AUTOEXEC.bin` 载入点（Thumb） |

> 这些地址**只用于说明结构**。要定位到具体函数/字段，需要自己做地址换算 + 交叉引用扫描——这是刻意保留的门槛。

**方法论**：每条结论先做静态字节级复核（反汇编 + 表结构还原 + 交叉引用扫描），再上机只读验证（Peek / 计数桩），最后才考虑写操作。上机前先跑对照（"只重映射、不改值"），出错后先怀疑**测试设备**（本轮就栽在这上面）。

## 怎么用

**这个仓库不是给人"用"的，是给人"读"和"复核"的。**

- 想理解机制：按 [docs/](docs/) 的顺序读，01 讲证据分级与地址换算，后面按主题展开。
- 想做静态复核：你需要**自己**合法持有的固件镜像、一套 AArch64 反汇编工具、以及耐心——核心结论都给了地址类别与结构，可以逐层对。
- 想复现实机实验：**本仓库不提供步骤**。原因有两个：这些操作要么会改变相机状态（卡启动、BootDisk 标志），要么在写错时会把 PTP 任务写死（Peek/Poke 无边界检查）。
- 想直接刷机：**没有这个东西**。本项目所有改动都是 RAM-only；会留在机身上的东西是 BootDisk 标志（可以清，但要显式清）。

**普通用户不要尝试。** 这里面没有任何一步是"跟着复制粘贴就能安全完成的"。

### 哪些能在离线做，哪些必须上机

| 内容 | 需要实机？ | 风险 |
|---|---|---|
| 反汇编、交叉引用扫描、表结构还原 | ❌ 纯离线 | 无（只读文件） |

6. **不要在没有退路的情况下上机**：卡死时先取卡再装电池；起不来先把卡取出来再开机。
