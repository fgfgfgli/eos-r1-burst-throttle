## 2. Astra（GPT-6 Astra）：冷启动卡执行的路线评审

### 2.1 最有价值的一条：拆掉"BootDisk 只写不读"的方法论漏洞

本项目曾有一个阶段性结论："全机 BootDisk 只写不读"（依据是扫描出 102 处写入、0 处读取）。

**复核意见指出的漏洞**（`[I]`，但很有说服力）：

1. **启动期的 ISA / 处理器不在扫描域内**——如果那段代码跑在另一个核上（Xtensa / S1 侧），扫主镜像当然扫不到；
2. **指针、镜像、宽读、间接访问**都会漏检——"0 命中"只约束了"这种搜索表示法在这个范围内"；
3. **把"S1 被命令驱动"误当成"整机不自动启动"**——两者不是一回事。

**结论**：那 102 处应当保留为**局部发现**，不能升格为全称命题。

### 2.2 排序建议

复核意见认为**不该按 A→B→C 顺序推进**：C 立即收窄；B0 先定地址域与真正的启动端；F0 优先查"现成 FAEXE 的自主触发者"（比新造一条路更划算）；A 在读卡条件成为具体缺口时再推进。

> 本项目实际走的路线**部分采纳**了这条：最终成功的桥不是"新造一条路"，而是**复用已有的复位流程 + 换页表源**——与"F0 优先查现成机制"的精神一致。

### 2.3 它给的验收清单（很值得抄下来）

复核意见提出，要声称"零持久卡执行"，必须逐项闭合：

| 必要项 | 什么算闭合 | 什么**不算** |
|---|---|---|
| 冷启动根 | 失电后的原厂路径能到达，前置状态来源明确 | 上次留下的 RAM、软重启、USB 下发事件 |
| 自动触发 | 启动任务/控制器**自主**产生事件或命令 | "S1 有 cmd6 handler"、"目录里有程序名" |
| **零持久条件** | 所需机身状态**原本满足**，或完全由瞬态流程得到 | 改 BootDisk/工厂标志后"还能恢复" |
| 文件来源 | 正确槽 / 文件系统 / 文件名 / 数据长度接到 loader | 看到某个字符串、或单独扇区读取成功 |
| 执行边 | 最终控制转移到**文件派生字节**，ISA/地址域/入口一致 | DMA 描述符存在、文件读取返回成功 |
| 稳定交接 | 主副侧同步、清零/覆盖范围、返回/存活与失败出口已知 | 只跳回原厂 reset，或只看屏幕正常 |

### 2.4 用它对照 11-17 的桥：**逐项过一遍**

> ⚠️ 上一稿在这里写错了。它把前五项宣布"全部闭合"，并说 11-17 的成功"推进了'无需新增持久状态'链"。
> **错在第三项**：桥成功的前提是 **BootDisk 此前已被开启**（会话记录明确写着"BootDisk 标志此前一直开着，清除命令未执行"），而 BootDisk 是**机身持久状态**。
> 原评审 §二/§六的原话是：**可逆的 BootDisk 持久写仍然不符合严格目标。**

正确的逐项对照：

| 必要项 | 桥的实际状态 | 判定 |
|---|---|---|
| 冷启动根 | 桥取代复位片段，失电后确实从卡上走 | **在"BootDisk 已开"前提下闭合**；若要求出厂默认状态，则前置条件不满足 |
| 自动触发 | 卡的读取与 kick 是启动流程自主产生的，不需要 USB | **在"卡上有载荷 + 标记 + 标志开"前提下闭合** |
| **零持久条件** | **依赖一个持久标志（BootDisk）** | 🔴 **未满足**（它可逆，但可逆≠不存在） |
| 文件来源 | 卡根载荷被读到、解码/跳转被执行 | 闭合（但只验证了两类载荷） |
| 执行边 | 控制确实转移到我们重编码的复位片段（否则补丁不可能出现在开机后） | 闭合 |
| 稳定交接 | 只验证了一种最终载荷；主副侧同步、清零/覆盖范围、失败出口没有穷尽 | **部分闭合** |

⇒ 所以正确的表述是：

> **在 BootDisk 已启用、卡标记与载荷已准备的条件下，冷启动桥成功。**
> **未证明出厂默认状态下"零持久写"的目标。** 那个目标**未满足，也未证明不可能**。

### 2.5 它的最终答复（写于 11-16）

> "严格目标仍未证实现，也未证不可能。下一份有价值的结果应是'普通冷启动 → 无需新增持久状态的触发 → 卡文件 → 执行入口'的闭合链。"

**这句话至今仍然成立**：11-17 晚上的桥走的正是另一条路——**先要一个持久标志**。它证明了"卡上代码能在冷启动参与启动流程"，但**没有**满足"无需新增持久状态"。

## 3. 所以"桥成功"到底算什么

| 说法 | 是否成立 |
|---|---|
| "卡上代码在冷启动时被执行了" | ✅ `[V]`（在 BootDisk 已开的前提下） |
| "补丁在开机后已经生效" | ✅ `[V]`（开机后只读回读 + 行为改变） |
| "整条链不需要 USB" | ✅ `[V]`（成立） |
| "达到了零持久卡执行" | ❌ **不成立**（依赖 BootDisk 这个持久标志） |
| "出厂默认状态也能用" | ❓ **未证明**（本来就是 `[?]`，本稿明确保留） |

⇒ 本稿的处理：**保留成果，不撤销**；**但把前提写在结论的同一句里**，不留"看起来是零持久"的余地。

## 4. GPT 复核：把工具链的问题逐条挖出来

### 4.1 最有价值的一条：`x1` 的更正仍然是错的 `[V]`

早期文档写"回调第二个参数 = 程序区末尾的回调槽"。复核者用逐指令追踪指出：在那个位置 `x19` 已经被改成 loader 刚填好的**接口块**地址，随后 `mov x1, x19`。

⇒ **回调的第二个参数是接口块，不是回调槽。** 复核者措辞很到位：

> "现有新载荷没有依赖这个 `x1`，因此此错不单独证明新载荷必崩，但它会**误导后续接口设计**。"

### 4.2 最具预见性的一条：callee-saved 寄存器 `[V]`/`[I]`

复核意见指出：载荷的入口与回调大量改写被调用者保存寄存器，但出口只恢复 x30，"只保存 LR 即可"不成立；而且 **loader 自己的保存不能替代载荷保存**——loader 的帧保存了 x19/x20/x21/x22/x29/x30，**没有保存 x23–x28**。

它还留了一句很克制的边界：

> "正常奇数出口会让 loader 用 SP 恢复它自己保存的那些寄存器，因此不能断言'每条 op 必然当场崩溃'。**ABI 违规已证，具体哪条调用链因此出错属 `[I]`。**"

**这条后来被实机证实了**：连拍节流早期版本的桩没保存 x18–x21，成了 **Err70 的元凶之一**（见 [05](05-burst-throttle.md) §5.2）。

### 4.3 其它被采纳的更正

| # | 复核意见 | 影响 |
|---|---|---|
| A3 | 载荷的写入门禁用**未规范化的 width** 算 `end = va + width`，之后只判断 1/2/8，其余一律按 4 B 写，随后无论多宽都做 4 B 回读 ⇒ 存在可复算的越界反例 | 载荷的写入门禁被重写 |
| A4 | 固件调用白名单**限制的是函数槽，不是实际操作** | 不能拿"白名单里有"当"操作安全"的证据 |
| A5 | 31 位数据"绕开最高位"的算术自相矛盾 | 该论证被删 |
| A6 | `OUT` / `PERSIST` 的数据链路**没接起来** | 相关结论降级为 `[?]` |
| B3 | **3000 / 80000 是场景超时上限，不是"等够了才重试"** | 直接推翻了"缩短延时可缓解 BUSY"的推荐（但 E1 的"恢复变快"仍待解释，见 [05](05-burst-throttle.md) §2.1） |
| B4 | "619 条直接 `BL` 里没有 MEMCOND"确认；但由它推出的**数据隔离结论不成立** | 负结论收窄 |
| C1 | MovieKind 的**有效标志读反了** | 视频链的统计重做 |
| C2 | "模式只有名字、没有编号"被遗漏的前置检查推翻 | 同上 |
| C5 | 格式表里有某个记录只能证明该记录存在，**不能证明 4000 行格式通过** | 6K 全高的概率判断下调 |

### 4.4 它点名的"最可能错的 3 处"

1. **"新工具载荷已经具备安全、可重复使用条件"**——回调 `x1` 解释错误、callee-saved 未保存、WRITE 宽度/回读越界、CALL 分派无实际操作白名单、状态与数据冲突，且 OUT 未接到 PERSIST。"哈希/可反汇编/自写模型通过，不足以覆盖真实调用上下文。"
2. **"3000/80000 是重试等待，缩短到 250 可缓解 BUSY"**——"应撤回该推荐，而不是只给延时单位加问号。"
3. **"全高表项 + MovFULL 名字 + 6K/29.97 记录，使视频管线大体可接"**——有效标志反读、候选封装只返回两个值、模式→timing→读出→输出→编码没有贯通。

> 三条全中。第 2 条后来由 E1/E2/E3 三组实验独立验证（缩短延时确实让"恢复变快"，但**不改变"为什么会停"**，而且改到 50 ms 会直接 Err70）。

## 6. 这些错是怎么发生的（比错误本身更有用）

| 错误类型 | 例子 | 怎么防 |
|---|---|---|
| **把默认值当异常** | 判决函数的 `A=14 / Vsize=0xFFFF` | 先读一遍**干净状态**的基线 |
| **把相似当相同** | cap 54 vs 55；显示侧 resize vs 录制路径 | 名字相近不等于同一条链，必须有**调用边**证据 |
| **把局部当全局** | "BootDisk 只写不读"；"没有写卡输入" | 负证据必须写清搜索域与表示法 |
| **把保护代码当成已生效** | "封顶到上一帧间隔"自指 | 保护性代码**必须能被证明生效**（日志/回读） |
| **把"没反应"当"成功"** | BootDisk 开 + delay 载荷 → 黑屏 | 区分"相机停住了"与"我们的代码跑了" |
| **停在第一个合理假设** | "停是配额造成的" | 做**短路实验**：把假设的机制整个关掉，看现象是否消失 |
| **把观测当机制** | "59.9 = 帧率"、"300ms 保证恢复" | 写清窗口/参数，机制另标 `[I]`/`[?]` |
| **在故障态里继续操作** | 黑屏时再装第二个探针 | 先冷启动，再动手 |
| **整表偏移没被前几行发现** | 工厂命令表 handler 列错位 | 整表按字节重读，不要只抽检前几行 |
| **照抄源文件的算术** | `+0xD000` | 源文件也会写错；关键数值自己算一遍 |

## 7. 对读者的建议

如果你要接着做这条线：

1. **先读 §5 那三张表**，别重复我们已经踩过的坑；
2. **任何"异常值"先做基线对照**（断电重启读一遍）；
3. **任何"保护性逻辑"都要能被证明生效**；
4. **负结论一律带边界**；
5. **观测与机制分开写**；
6. **把结论送出去让人拆**——本项目最值钱的几条更正全部来自外部复核，而它们全部是"我们自己看不出来"的。
