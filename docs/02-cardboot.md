# 02 · 卡启动：BootDisk + AUTOEXEC

> **Credit / 署名**：Canon EOS R1 research by **fgfgfgli** — 基于本文做新机型研究时，请注明作者并附仓库链接（CC BY-NC 4.0）。 / If you build on this, credit the author and link <https://github.com/fgfgfgli/eos-r1-firmware-research>.


> 目标：让相机**冷启动时**从 CFexpress 卡执行我们自己的代码，不使用 USB。
> 结论：**在"BootDisk 已启用、卡标记与载荷已准备"的条件下，冷启动驻留桥成功**；但**出厂默认状态下的零持久写**这个更严格的目标**没有证明**（见 §6）。
> 另外，最后成功的路径和最初的设想完全不同——不是"写固件"，而是"接管页表源"。

## 1. 这条链上到底有什么

### 1.1 复位入口不是函数 `[V]`

主镜像入口 `0xE0500000` 是 **AArch64 复位向量**，跑在 **EL3**：

- 先配 `SCR_EL3` / `HCR_EL2` / `ACTLR_EL3` / `VBAR_EL1..3` / `CNTFRQ`；
- 再设 `SPSR_EL3` / `ELR_EL3`，`eret` 落到 **EL1h**；
- 结尾是 `bl …; b .` —— **永不返回**。

⇒ 所以"先调用 `0xE0500000`，返回后我们打补丁"这种 R5M2 式做法在 R1 上**不成立**。这是本项第一个被排除的方案 `[V]`。

### 1.2 页表是在入口内部、MMU 打开之前建好的 `[V]`

顺序（都在 `0xE0500000` 之内）：清零页表 SRAM → 拷入 cache 维护例程 → 拷入**页表 blob** → 置 `sctlr_el1.M = 1`（MMU 打开）。

⇒ **运行期的第一套表就是这块 blob**；在有界扫描范围内**没有观察到**开机后有新的 `TTBR` 写入（见 [04](04-mmu-and-remap.md) §1.4 的范围与限制）。这条事实决定了整个方案：**想"一开机就带补丁"，就要在拷贝之前把源换掉。**

> ⚠️ 别把"没观察到新 TTBR 写入"读成"表不可能被改"：**不换基址**也可以直接改**表项内存**，而那种写不在本节扫描的范围内。低地址段的另一套内核也未知 `[?]`。

> blob 的源地址、大小与 SRAM 目标地址不在公开版。

### 1.3 谁把 PC 设成卡载荷地址 `[V]`+`[I]`

不是"调用"，是"设 PC"：DIGIC X 家族由 source-0（Xtensa Pino）在 cmd5/cmd6 之后把主 CPU 入口写成 `McpuKickAddr`——**有卡载荷时 = 卡载荷载入地址，无卡时 = 复位入口**。R1 的 S1 侧 cmd5/cmd6 已在 part2 定位，与 R5M2 同架构 `[I]`。

### 1.4 AUTOEXEC 被跳转时的环境 `[V]`+`[I]`

**EL3、MMU 关、D-cache 关、I-cache 关、SP 无效、VBAR 未设。**

所以：可以读计数器、可以做 cache 维护、可以 `tlbi`；但**不能假设任何 OS 设施存在**（R5M2 上早期版本因为读 timer 直接黑屏）。

> ⚠️ 更关键的坑：**stage-1 处于 EL3 安全态（`SCR_EL3.NS` 未置位），写非安全 DRAM 不可靠。** 本轮实测：所有数据写入必须放到 EL1 的 wrapper 里做。见 §5 教训 3。

## 2. 卡侧准备

与 R5M2 公开指南同构：在 exFAT 的**主启动扇区与备份启动扇区**里写两个标记字符串，并**按 exFAT 规范重算两份启动区的校验和**。改动范围很小（个位数扇区），动手前必须完整备份原始启动区。

> 🔴 **标记偏移、标记字符串在扇区内的位置、校验和算法与存放位置、受影响的扇区数、备份方式，全部不在公开版。** 这是 R7 判定"公开颗粒度过细"的第一处：给了这些，就等于给了"造一张开机能跑代码的卡"的能力。需要的话请自行研究 exFAT 规范 + 你自己设备的行为。

卡根放两个载荷：`AUTOEXEC.bin`（AArch64，载入 `0x09000000`）与 `S1_AUTOEXEC.bin`（Thumb，载入 `0x00800000`）。载荷是**平坦二进制**，没有节加载、没有自动重定位。

> 🔴 **标记偏移、标记字符串在扇区内的位置、校验和排除字节、校验和存放扇区、写扇区的步骤，全部不在公开版。** 这是 R7 判定"公开颗粒度过细"的第一处：给了这些，就等于给了"造一张开机能跑代码的卡"的能力。需要的话请自行研究 exFAT 规范 + 你自己设备的行为。

## 3. A/B 对照：BootDisk 标志到底门控了什么

同一张带标记的卡、同一个 `AUTOEXEC.bin`（delay 载荷：空转后跳原厂入口），**只切换机身 BootDisk 标志**：

| 组 | BootDisk | 结果 |
|---|---|---|
| A | 关（`DisableBootDisk`） | **正常开机** |
| B | 开（`EnableBootDisk`） | **完全没反应**（长时间不亮灯） |

### 3.1 能下的结论 `[V]`

BootDisk 标志确实门控了一条"读取并执行卡上代码"的路径。

### 3.2 不能下的结论 `[?]`

**这组对照不能证明"卡上代码跑了"。** 它只证明相机停在了某处。另一种解释是：标志打开后相机去**读卡**，而这张自制卡读取失败，导致挂起。

**当时没有排除这个解释。** 所以这条记录的措辞必须是"标志门控了一条路径"，而不是"卡启动成功"。

### 3.3 旁证：safe / hang 载荷 `[V]`

| 载荷 | 行为 | 结果 |
|---|---|---|
| safe | 立即 `br` 到原厂入口 | **正常开机** ⇒ 加载器能读卡、能跳转 |
| hang | `b .`（死循环） | **Err02 / 卡死**，需取电池 |

hang 载荷是**强旁证**：如果卡上代码没被执行，一个死循环很难解释 Err02。
但它**不是排他性逻辑证明**——Err02 也可能来自"读到坏数据后原厂代码自己判定失败"。所以本节把它记作旁证，不记作"执行已被证明"。

## 4. 两个"载荷能否改写主固件内存"的探针：仍未定论 `[?]`

拿到执行权之后，第一个想法是"直接改固件"。两个探针都指向"不行，但没证死"：

| 探针 | 做法 | 结果 | 两种解释 |
|---|---|---|---|
| `uitest` | 把版本串改成 `9.9.9`，做 cache 维护 | 正常开机；菜单与 USB 上报**仍是 1.3.0** | 写没落到运行时用的那份内存 / 该串不是显示来源 |
| `persist` | 把主入口首条指令写成死循环，然后跳过去 | "延迟了一下，然后正常开机" | ①写没落到活内存；②写生效了，看门狗复位后正常启动 |

**为什么不定论**：两者都无法区分"写没落地"和"写落地了但没影响"。

**后来怎么解决的**：不再试图写固件，而是**换页表**。这条路彻底绕开了"介质只读"的问题——见 [04](04-mmu-and-remap.md)。

> 顺带一条静态事实：`0xE0500000` 所在的介质**看起来是** ROM 镜像窗口（MMU 层却是 RW），写只停在 D-cache，几分钟后回退 `[V]` 观测 / `[I]` 解释。细节与反面证据见 [04](04-mmu-and-remap.md) §2。

## 5. 冷启动驻留桥：成功的那一版

### 5.1 设计思路

不写固件、不在 MMU 之后抢执行权。**取代复位片段本身**：

1. 把复位代码整体搬到 RAM，重编码其中所有 PC 相对指令（`ADRP` 重编码 + `BL` 走 veneer 表）；
2. 把"页表拷贝源"从原厂 blob 换成**预打过补丁的 blob**；
3. 在它调用 cache 清洗例程的那一处挂一个 wrapper；
4. wrapper 做完所有事之后，**tail-branch** 回原厂流程。

⇒ **MMU 一打开就已经带着补丁**，我们自己的代码不需要在 MMU 之后运行。这是本方案最核心的风险控制。

### 5.2 wrapper 做了什么（概念级）

生成一张身份映射的 L3 表 → 把两个目标代码页拷到页表空洞区的副本 → 在副本里写跳板 / 改重试常量 → 把对应的 L2 条目改成指向新 L3 → 做 cache 维护 → 恢复 LR，tail-branch 回原厂。

> 具体的页号、槽位、偏移、跳板字节、副本地址、L2 写入值、cache 指令顺序**全部不在公开版**（内部记录里有）。这一节只说明"它做了哪几件事、为什么这么排"。

### 5.3 实机复核（只读）`[V]`

开机后**不插任何额外设备**，只用 USB 只读回读：L2 条目已指向新 L3；L3 恒等项符合预期；被 hook 的函数入口首字是跳板；两个页副本在页表空洞区且被执行到（连拍行为改变）；重试常量两处都变成了目标编码。

⇒ **在 BootDisk 已启用、卡标记与载荷已准备的前提下，开机自动打补丁成立，全程不需要 USB。** 连拍实测：不崩、降速生效（幅度受卡写速限制）。

### 5.4 五个坑（按代价排序）

| # | 坑 | 后果 | 教训 |
|---|---|---|---|
| 1 | **坏卡混淆** | 同一载荷时好时坏；后来越简单的载荷也不启动；整段实验结论作废 | **实验前必须做基线**：safe 载荷连开 3 次。任何不一致先怀疑卡 |
| 2 | 编码器的立即数被截断 | 循环增量变 0 → L3 全项指向同一页 → 黑屏 | 编码器要加断言 |
| 3 | EL3 下写非安全 DRAM 不可靠 | stage-1 里写的数据丢失 | 所有数据写入放 EL1 的 wrapper |
| 4 | wrapper 里 `blr` 原厂函数再 `br` 返回 | LR 语义混乱 → 崩溃 | **必须 tail-branch** |
| 5 | 低区载入地址开机后被清零 | 放在那里的持久数据消失 | 持久数据放**页表空洞**（canary 实测存活） |

### 5.5 这一版成功之前发生了什么

值得记录，因为它演示了"归因错误"是怎么发生的：

- `reloc_safe`（只搬移，行为不变）→ 正常开机 ✅
- `hook2`（加一个空 wrapper）→ **正常开机一次**，之后同文件黑屏 ← 这里就应该怀疑卡
- `hook3`（wrapper 只写一个 magic 字）→ 黑屏 / Err02
- `bridge`（完整版）→ Err02 / 黑屏
- **`AUTOEXEC.safe`（512 B，只有 `ldr` + `br`）→ 后来也黑屏、背光不亮**

最后一行是转折点：**连"什么都不做"的载荷也不启动**，才让人意识到是卡在实验过程中失效了（此前还出现过启动标记莫名消失）。换一张格式化后的好卡，bridge 一次通过。

⇒ 所以：**"今天后半段的 hook3/bridge 失败"不能归因于桥代码**，只能归因于测试链路。

## 6. 关闭、恢复与边界

### 6.1 关闭

卡上删掉（或改名）`AUTOEXEC.bin` **并且**清掉启动标记。

> ⚠️ **只删文件、标记还在 ⇒ Err02。** 两个必须一起清。

### 6.2 恢复（起不来的时候）

- 桥只改 RAM / 页表 / 卡上文件，**断电即恢复**——但这条**只管 RAM**：BootDisk 标志与卡上的标记/文件**不会**因为断电而消失；
- 起不来就**先把卡取出来再开机**：卡不在，就没有 `AUTOEXEC.bin` 可读，走原厂路径；
- 卡死取电池时，**先取卡再装电池**。

> 复核意见（R1 附图）指出：上一稿把"卡上没 `AUTOEXEC.bin` 就走原厂路径"与"标记还在只缺文件会 Err02"并列，读起来像通用保证。本稿已限定为**取卡后**，并明确"标记仍在而只缺文件"是 Err02。

### 6.3 边界（必须写清）

| # | 边界 | 等级 |
|---|---|---|
| 1 | **成功有前提**：BootDisk 此前已开启、卡标记与载荷已准备。**出厂默认状态下的"零持久写"目标没有证明** | `[V]`（前提）/ `[?]`（严格目标） |
| 2 | 只验证了"打上连拍节流补丁"这一种载荷；换别的载荷是否同样稳，**未测** | `[?]` |
| 3 | 与安全启动 / 签名校验的关系**未查清**。我们改的是"页表拷贝源"，不是签名本身；文档里**没有任何**"绕过签名校验"的结论 | `[?]` |
| 4 | BootDisk 标志是**持久**的，必须显式清除；这一点与 RAM-only 的补丁不同 | `[V]` |
| 5 | 桥依赖复位入口内部的具体指令序列；**换固件版本必须重新核对**（本轮只在 1.3.0 上验证） | `[V]`（限制本身） |
| 6 | 卡启动链路的稳定性高度依赖卡的质量与读取链路；坏了会伪装成"代码 bug" | `[V]` |

### 6.4 关于"零持久条件"这个更严格的目标

这个项目最初想要的目标是：**普通冷启动、不新增任何持久状态、卡文件派生的代码被执行**。

晚间的桥**没有**达到这个目标，它达到的是：

> **在 BootDisk 已启用、卡标记与载荷已准备的条件下，冷启动自动打补丁成功。**

两者的差别不是措辞：BootDisk 标志是**机身持久状态**，清掉它需要显式操作，而且它正是"让相机去读卡"的那个开关。外部复核（`analysis/ROUTE-REVIEW-ASTRA.md`）对此有一句明确的话：**可逆的 BootDisk 持久写仍然不符合严格目标。**

⇒ 所以本项的正确记法是：**桥的成功是真实成果**（`[V]`，有开机后只读回读与用户手感），但它**不能**替代"零持久写"这个严格目标；后者**未满足、也未证明不可能**。

## 7. 与 FAEXE 那条路的区别

| | 卡启动（AUTOEXEC） | FAEXE |
|---|---|---|
| 触发 | 冷启动，自动 | 工厂命名命令，需 USB（或卡根 `faexe.bin` + 命令） |
| 执行环境 | **EL3，MMU 关** | **EL1，MMU 开** |
| 能做页表操作 | 可以，但写非安全 DRAM 不可靠 | 可以，稳定 |
| 断电后 | 自动重来（**前提是 BootDisk 仍开着**） | 需要重新触发 |
| 适合 | 开机就生效的驻留补丁 | 交互式实验、探针 |

两条路的**汇合点**是本项目的最终形态：**卡启动桥负责"开机自动把页表换掉"，页表换掉之后的一切（跳板、桩、参数）与 USB 路线共用同一套构建器。** 详见 [03](03-usb-factory-channel.md) 与 [04](04-mmu-and-remap.md)。
