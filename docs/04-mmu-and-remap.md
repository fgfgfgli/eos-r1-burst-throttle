# 04 · 页表权限与重映射

> 本文解释一件反直觉的事：**为什么"能写固件"是假的，"能改代码"却是真的。**
> 这也是整个项目从"改固件"转向"换页表"的分水岭。
>
> 公开版只到机制与证据等级；页表槽位、页副本地址、描述符写入值、cache/TLB 维护序列不在公开版。

---

## 1. 先看清楚：MMU 说可以写

### 1.1 目标地址怎么走表 `[V]`

以**镜像区内某个 2 MB 代码块**为例（本节**不点名**具体补丁页，也不给页表基址与槽位——那三个值在内部记录里）：

| 层级 | 观察 |
|---|---|
| `TTBR0_EL1` | 一级表基址（值不在公开版） |
| L1 项 | 指向一张 L2 表（基址不在公开版） |
| L2 项 | **2 MB block** 描述符（值不在公开版） |

描述符解码（ARM 架构字段，结论与具体地址无关）：

| 字段 | 值 | 含义 |
|---|---|---|
| 类型 | `01` | block（不是 table，也不是 page） |
| PA | 与该块 VA 恒等（2 MB 对齐） | 恒等映射 |
| AP[2:1] | `00` | **EL1 可读写**；EL0 无访问权 |
| AttrIndx | `0` | Normal memory，Write-Back |
| SH | `3` | inner shareable |
| AF | `1` | 首次访问不 fault |
| **nG** | **`0`** | **global**（不是"非全局"——上一稿写反了，此处按 ARM 架构定义更正） |
| PXN / UXN | `0` | 可读可执行 |

⇒ **EL1 里对镜像区代码页直接 `str` 不会 permission fault。** 这一条把"改不了固件"的直觉推翻了一半，也是全篇唯一真正需要"地址"才能得出的结论——而它**不需要**具体地址：AP=00 是整段镜像区的统一策略。

> 具体基址、槽位与描述符原值已移到内部记录（R7/N09：上一稿把它们留在公开篇，却声称"已全部移走"——那是自查不实，本稿已修正）。

### 1.2 权限表的整体形状 `[V]`

- 固件镜像区 `0xE0500000`–`0xE2F00000` 是**统一的 Normal WB / RW**；
- 4 GB 空间里绝大部分是**恒等映射**（PA = VA）；
- `TTBR1` 在启动期基本是空的。

### 1.3 页表本身放在哪 `[V]`

`0xDFFC0000` 起的 SRAM。它不是现场算出来的，而是**镜像里的一块模板被整块拷进去**：启动代码先清零这块 SRAM，再拷入 cache 维护例程与页表 blob，最后才打开 MMU。

⇒ **在有界扫描范围内，没有观察到开机后有新的 `TTBR` 写入**，所以"运行期第一套表来自这块 blob"是 `[V]`。这条事实是卡启动桥的基础（见 [02](02-cardboot.md) §1.2）。

### 1.4 运行期会不会改表：只在一个范围内有结论

> `[V]`（**有界**）**就 ROM 段而言**，对全部 AArch64 段做 MMU 配置寄存器写入的原始编码扫描：`msr ttbr0_el1` / `tcr_el1` / `mair_el1` 各只在启动那一段出现一次，**没有观察到 ROM 代码此后再写这些寄存器**。
>
> `[?]` **这个扫描有两个盲区，必须一起说**：
> 1. **"没换基址" ≠ "表没被改"**——代码可以直接写**表项所在的内存**，这种写不经过 `msr`，不在本节扫描范围内；
> 2. **低地址段还有一套**：扫描发现低地址段有 20+ 处 `msr ttbr0_el1`、40+ 处 `msr ttbr1_el1`，其中一处明显是"改 TTBR0 基址 + 往 TTBR1 塞 ASID"的地址空间切换。但那些段的**运行期 VA 未确定**，所以"是否有另一套页表/另一次地址空间切换"**本轮无法定论**。

⇒ 由此**不能**推出"运行期目标页的权限不会改变"。上一稿写了这句，是超出证据的。本稿的结论只有两条：**（a）ROM 段里没有观察到换表；（b）其它路径未排除。** 目标页权限在长时间运行中是否变化，仍待证 `[?]`。

## 2. 然后看清楚：介质**看起来**是只读的

MMU 权限只管"CPU 允不允许"，**不管"介质收不收"**。这两件事必须分开。

### 2.1 支持"介质只读"的证据（解释，不是排他证明）

| # | 证据 | 等级 |
|---|---|---|
| 1 | 启动期把页表、cache 例程、运行库**全部复制出去**，然后对副本做 cache 维护 | `[V]`（行为） |
| 2 | `[I]` 这样的行为**通常**出现在源不可写时——但"复制出去"也能出于别的理由（例如统一 cache 策略、避免 XIP 的性能问题），所以**不是排他性证明** | `[I]` |
| 3 | 全量扫描**零条**静态的"写固件区"全局写 | `[V]`（有界） |
| 4 | 同一平台的公开研究材料把这一整段写作 **source-0 ROM 有效范围** | `[V]`（材料事实）/`[I]`（R1 同理） |
| 5 | 已知的同平台 OpenGate/卡启动实现都是"拷页到 RAM → 改副本 → 换映射"，**不是**改 flash | `[I]` |

### 2.2 支持"就是可写 RAM"的证据（也必须列出来）

| # | 证据 | 等级 |
|---|---|---|
| 6 | 页表把它映射成 RW + Normal WB。若真是 ROM，通常应映射成 RO 或 Normal-NC | `[V]` |
| 7 | EL3 的 secondary-core 代码把 `SP_EL1` 设成镜像区内的一个地址且内容非零。若该区只读，这个栈用不了 | `[V]`（指令）/`[?]`（是否真会走到） |

### 2.3 决定性的实机观测 `[V]`

同一次会话里的对照（这是最干净的一次）：

- 连续 4 次向镜像区目标地址 `Poke32` 新值：请求**全部成功返回**、会话正常结束、**没有 fault**；紧接着 `Peek32` 读到**新值**；
- 隔几分钟、换会话再读：**回到镜像原值**；另一个表项同样"写入成功 → 回读到新值 → 数分钟后回退"；
- 同一时段对**普通 RAM** 地址写同一个 canary：**一直保持**。

**读法**：MMU / 指令层面完全成功（与 §1.1 的 RW 判定一致）；写只落在 **write-back D-cache** 的脏行里，同核读命中脏行 ⇒ 回读是新值；脏行被淘汰或清理时，写回目标若不可写就**被丢弃**，再读回就是原值。最后一条是关键：**同一时刻，RAM 里的值还在，镜像区的值已经回退**——这排除了"相机只是重启了"的解释。

> 这条解释是 `[I]`，不是 `[V]`：我们**没有**直接观测到"脏行被丢弃"这个事件，只观测到"回读回退"。它是最符合所有观测的解释，但严格说仍可设想别的介质语义。

### 2.4 综合判断

> `[I]`（强）：`0xE0500000`–`0xE2EF2FA0` 是**原厂 ROM 镜像窗口，只读**；页表给的 RW 是整段 144 MB 的粗策略，不代表介质可写。
>
> `[?]` 残余不确定性：有两段时间窗没有 RAM 见证值，理论上不能 100% 排除"期间相机重启过"。要彻底钉死，需要一次"写镜像区 + 写 RAM 金丝雀 + 隔一段时间同时回读"的实验。

> ⚠️ 上一稿把"复制出去只有只读源才需要"与"D-cache/介质只读"写成了 `[V]` 级的排他证明。**本稿已降级为 `[I]` 并列出反面证据**（复核意见 R6 的第 3 点）。

## 3. 于是：重映射

### 3.1 原理

不改介质，改**地址翻译**：

```
拷贝目标 ROM 页 → RAM 副本 → 在副本上打补丁
把 L2 的 2 MB block 描述符 → 换成指向一张 L3 表的 table 描述符
在 L3 里把目标 4 KB 页指到 RAM 副本，其余 511 项保持恒等映射
维护 cache 与 TLB
```

⇒ CPU 之后取到的就是我们改过的页。**ROM 一个字节都没动。**

### 3.2 为什么一次要建好几张 L3 表

因为一次实验往往要改**多个 2 MB 块里的页**（代码页、CAP 表页、DS 几何页）。每张 L3 表管一个 2 MB 块，512 项 × 4 KB = 2 MB，正好覆盖。

这些表与页副本都放在**我们自己的可执行 RAM**里（已分配、可写、足够大）。**具体地址、槽位与大小不在公开版。**

### 3.3 必须做的收尾 `[V]`

改完页表之后必须做架构要求的 cache 与 TLB 维护，**顺序不能错**，而且：
- 改**代码**页时，必须做**指令 cache** 的全失效——漏掉的后果是"数据看着变了、执行还是旧代码"，极难 debug；
- 改**数据**页时不需要指令 cache 失效（做了也无害）。

> 具体的指令序列（哪几条 `dc` / `dsb` / `tlbi` / `ic`、屏障级别、覆盖范围）不在公开版。
> 公开版只保留判据：**"改了代码就必须让取指路径看到新字节"**——这是任何 AArch64 上的常识，但漏掉它是本项目真实踩过的坑。

固件自己带了 cache 维护例程（固定在 SRAM，可直接 `blr`）。本项目优先用它们，避免自己写 cache 细节出错。

### 3.4 幂等性（能重复跑）

模块开头**先把 L2 描述符恢复成原厂值**，再建表。

理由：如果上一次运行已经把描述符换成 table，第二次运行时若直接"读原描述符 → 算新值"，就会读到自己的产物，越跑越乱。先恢复、再重建，才能"重复运行不污染"。

### 3.5 实机验证 `[V]`

装好之后**等 20 秒**（不是立刻）回读：L2 槽都指向我们建的 L3 表；L3 里的恒等项值正确；目标地址读到的是**补丁后**的值；CAP 表项读到的是改后的值。

后来的卡启动桥版本在**冷启动后**复核同一组结构，同样一致 ⇒ 机制不依赖 USB 会话（见 [02](02-cardboot.md) §5.3）。

> 注意这里的边界：一次通过只说明**这次**通过，不构成"机制普遍安全"的证明（复核意见 R5 第 4 点）。

## 4. 回滚

| 方式 | 操作 | 何时用 |
|---|---|---|
| **最稳** | 关机断电重启 | 任何时候。页表与副本全丢，回到 ROM |
| 运行中撤销 | 把 L2 描述符写回原厂值 + 做 cache 维护 | 不想断电时 |
| 单模块撤销 | 跑一次该模块的 `--noop` 变体（只恢复描述符，不打补丁） | 调试期间 |

> 回滚**不需要**"恢复固件"——固件从来没被改过。这是重映射方案最大的好处。

## 5. 这条线的边界

| # | 边界 | 等级 |
|---|---|---|
| 1 | **对照实验**：只重映射、一个值都不改的版本，在这次配置下能正常录像 ⇒ 机制本身**这一次**没有引入故障 | `[V]`（一次观测） |
| 2 | 页副本在 RAM，断电即丢；页表描述符也在 RAM，同样断电即丢 ⇒ 整体 RAM-only | `[V]` |
| 3 | 两个模块可能抢同一个 L2 槽（同一个 2 MB 块）。默认 `merge` 复用既有 L3 可共存；`--replace-l2` 会顶掉先装的模块 | `[V]` |
| 4 | 改**指令**页必须做指令 cache 失效，改**数据**页不用 | `[V]` |
| 5 | 重映射不能解决"介质不可写"以外的问题（例如副核自己的代码，见 [07](07-open-gate-err70.md)） | `[V]` |
| 6 | 页表项的具体编码（bit 布局、属性值）是 ARM 架构规范，不是厂商秘密；但**具体写哪几个字**不在公开版 | —（刻意） |
| 7 | "介质只读"的解释有反面证据，且没有直接观测到脏行被丢弃 | `[I]` / `[?]` |

### 关于第 3 条：一次真实的冲突

本项目同时存在多个补丁模块，分属不同的 2 MB 块：

| 模块 | 所在块 |
|---|---|
| 6K 谓词 + AF 计数桩 | **同一个块**（必须共用同一张 L3） |
| AF 行模式 + 连拍节流 | **另一个块**（同样必须共用） |

⇒ "同块"的几组**必须共用同一张 L3 表**。构建器默认的 `merge` 模式就是干这个的；一旦有人图省事用 `--replace-l2`，先装的那个模块会**静默失效**——**它不会报错，只会不再生效**。

> 这是本类补丁最容易踩、最难查的一类 bug：**失效是静默的**。所以每次装完都必须回读验证。

## 6. 一句话总结

> MMU 允许你写，介质不接收你的写。
> 所以别改固件——**改它的地址翻译**。
