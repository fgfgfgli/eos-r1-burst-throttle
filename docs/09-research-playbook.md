# 09 · 研究流程：从一个问题到一条可复核结论

> **Credit / 署名**：Canon EOS R1 research by **fgfgfgli** — 基于本文做新机型研究时，请注明作者并附仓库链接（CC BY-NC 4.0）。 / If you build on this, credit the author and link <https://github.com/fgfgfgli/eos-r1-firmware-research>.


> 这份文档教的是**怎么研究**，不是**怎么复现本项目的补丁**。它适用于任何一台你想做互操作性/安全研究的相机。
> 具体机型的密钥、写卡偏移、钩子地址、载荷字节**不在公开版**——这里给的是方法、判据和安全边界。

---

## 0. 先回答三个问题，再动手

1. **你有权处置这台设备吗？** 不是"我买的"就够，还要看你所在法域允许做什么（见 [DISCLAIMER](DISCLAIMER.md) §4）。
2. **你要回答的可证伪问题是什么？** 例："连拍的停顿由缓冲水位决定，而不是帧数配额"——能被一次 A/B 推翻的，才是好问题。
3. **失败怎么恢复？** 断电、取卡、无卡开机、还原备份——**没有恢复路径的实验不要做**。

---

## 1. 证据分级（全项目通用）

| 等级 | 含义 | 例子 |
|---|---|---|
| `[V]` Verified | 直接观测到，且可重复 | 回读地址等于写入值；A/B 对照出现预期差异 |
| `[I]` Inferred | 由多条证据推出，但非排他 | "写入停在 cache 里"——回读一致但几分钟后回退 |
| `[?]` Unknown | 未证、或证据冲突 | "这个标志就是启动门"——只看到名字，没看到消费者 |

**每条结论都要带等级**；等级会随新证据变化，允许降级与撤回（见 [08](08-review-notes.md)）。

---

## 2. 三条证据线，缺一不可

| 线 | 你要拿到什么 | 常见坑 |
|---|---|---|
| **静态** | 明文固件、地址↔文件偏移、字符串/交叉引用、函数边界 | 把反编译当源码；忽略编译器优化 |
| **动态** | USB/PTP、工厂通道、内存读写、行为触发 | 把"能读"当成"能改"；写未映射地址卡死任务 |
| **行为** | 相机实际功能（连拍/对焦/录像） | 用单一现象下因果结论 |

**好结论 = 三条线互相印证。** 只有静态 ⇒ 标 `[I]`；只有行为 ⇒ 标 `[V]`（现象）但因果仍 `[?]`。

---

## 3. 建立 ground truth（在碰任何"修改"之前）

1. **身份**：型号、固件版本、序列哈希——每次实验前后都记；
2. **canary**：在 RAM 放一个已知值，验证"你读到的就是活的那份"；
3. **负对照**：不改任何东西，跑一遍，确认现象不出现；
4. **一次只改一个变量**：A/B 两组，其余全同；
5. **时间线**：所有日志带时间戳，事后能重建顺序。

> 本项目最贵的两次教训都在这条：坏卡让"同一载荷时好时坏"；把 cache 回读当成落盘。

---

## 4. 静态分析的工作顺序

1. **先验证地址换算**：用一条已知字符串/已知函数对齐文件偏移与虚拟地址，再谈别的；
2. **字符串 → 交叉引用 → 调用者**：名字只是线索，调用边才是证据；
3. **小函数先读汇编**，再信反编译；调用约定、寄存器保存、返回语义要逐条对；
4. **数据表/结构体用行为反推**：改一个字段看哪个消费者变化，比猜字段名可靠；
5. **每个结论都要能被"下一条指令"推翻**——写下"如果看到 X，则本结论错误"。

---

## 5. 动态通道的安全等级（按代价排序）

| 级别 | 操作 | 前提 |
|---|---|---|
| L0 | 只读枚举/Peek | 无 |
| L1 | 可逆 RAM 写（canary、临时桩） | 有回读验证 + 断电恢复 |
| L2 | 持久写（BootDisk 标志、卡标记） | **先备份**，写前有 dry-run，写后有回读 |
| L3 | Flash/校准/不可逆 | 不在研究范围 |

**写操作前先问：写错了会怎样？恢复要几步？** 答不上来就不要写。

---

## 6. 修改与验证的纪律

- 优先**非阻塞、可逆、RAM-only**；
- 失败先**回滚**再分析，不要在故障态叠加新改动；
- 验证用**双证据**：行为 + 回读，不靠单一现象；
- 记录**失败与被推翻的结论**——它比成功记录更能防止后人重复踩坑；
- 报告里写清"这个结论的边界"：换机型、换固件、换卡是否还成立。

---

## 7. 记录格式（让别人能复核）

每条结论至少包含：

```
问题：……
方法：……（A/B、变量、样本量）
证据：……（原始日志/回读值/哈希）
等级：[V]/[I]/[?]
边界：……（在什么条件下不成立）
反例/撤回：……
```

时间线单独记；原始日志保存哈希；**复核者只靠记录就能判断，不需要你在场**。

---

## 8. 迁移到别的机型：什么能复用，什么必须重做

| 能复用 | 必须重做 | 不能假设 |
|---|---|---|
| 研究方法与证据纪律 | 固件获取与解密 | 同名标志 = 同一开关 |
| 同 SoC 家族的公开知识 | 地址、页表布局、启动链 | 同平台 = 同地址 |
| 公开规范（exFAT、ARMv8 MMU） | BootDisk/启动标志的位置与语义 | 一个机型成功 = 全系通用 |
| 失败模式（坏卡、cache、写错地址） | 每机型常量与消费者 | 名字像就一定是它 |

**结论**：本仓库能让你少走弯路，但不能替你做另一台机器的研究。

## 9. 本仓库故意缺什么（不要在这里找）

- 固件解密密钥/派生参数；
- 卡启动标记的偏移、字符串位置、校验和算法、写扇区步骤；
- 钩子落点、桩/跳板布局与机器码、页表槽位与页副本地址；
- 工厂通道握手常量、载荷编解码格式；
- 一键写卡工具与任何可执行载荷。

缺这些是**设计**，不是遗漏。原因见 [PUBLISHING 原则]（内部文档）与 [README](README.md) 的"公开版保留了什么、移走了什么"。
