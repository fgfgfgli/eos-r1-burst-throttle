# 03 · USB 工厂通道与 FAEXE

> 这条线解决的问题是：**怎么在一台量产机上，不拆机、不刷机，跑一段自己的 AArch64 代码，并且能读写内存。**
> 答案分两层：USB 工厂会话（拿通道）+ FAEXE 加载器（拿执行权）。

---

## 1. USB 侧：设备暴露了什么

### 1.1 设备身份 `[V]`

相机以 WPD/MTP 设备出现，走 Windows 自带驱动，无需额外依赖：

| 项 | 值 |
|---|---|
| VID / PID | `04A9` / `3313` |
| 型号串 | `Canon EOS R1` |
| 固件（WPD 上报） | `3-1.3.0` |
| 厂商扩展 GUID | 与同平台机型同一个（本项目不重复列出） |

查厂商扩展能力表时有一个坑：**必须用读写句柄**。只读句柄会返回"拒绝访问"，很容易被误读成"设备不支持"。

### 1.2 能力表 142 项，但它不能当"能不能执行"的证据 `[V]`

R1 返回 142 个 opcode，前 12 个与同平台机型逐个相同 ⇒ 两机暴露的是同一套厂商扩展接口 `[V]`。

**但是**：真正要用的 `0x9052` / `0x9058` / `0x9059` / `0x905A` **都不在这张表里**。它们是"按名字 dispatch"的，不在能力枚举里。

> 这条教训值得单独记：**能力表查不到，不等于做不到。** 本项目早期因为"表里没有"而绕了很久的弯路。

### 1.3 握手 `[V]`

服务通道是三包 `data_out(0x905C, …)`，参数由型号与 PID 算出（不是固定的机身秘密）。本项目**不列出**具体握手值与计算式。

曾经有一个被误读的现象：发完握手再发 `0x9052`，**30 秒后**返回 `0x802A0006`（`E_WPD_DEVICE_IS_HUNG`），随后句柄不可用。

**这是超时/挂死，不是"被拒绝"。** 当时的记录把它写成"事件被拒"，是错的，已更正。从日志**推不出**"握手值无效"或"没进工厂模式"——它只能说明"这次调用没在 30 秒内返回"。

## 2. 按名字调用固件内部函数

### 2.1 工厂命令表 `[V]`

固件里有一张 `(name_ptr, handler_ptr)` 的 16 B 表（遇到 `name == 0` 结束）。`0x9052` 做的就是**按名字查表并调用**。

表里包括：`IsFactoryMode`、`IsAdjustmentSystem`、`InitializeAdjustmentSystem`、`TerminateAdjustmentSystem`、`AllocateFactoryProgramMemoryArea`、`GetFaexeWorkAddress` 等。

> ⚠️ 这张表的 handler 列在早期文档里**从 `Allocate…` 起整体错位一行**（把 `(name, handler)` 读成了 `(handler, name)`）。这类"整表偏移"错误极难发现，因为前几行是对的。本项目后来按字节重读整表才修正。

### 2.2 其中两个 handler 就是一条指令 `[V]`

| 名字 | 语义 |
|---|---|
| `Peek32` | 读一个 32 位字（实现就是一条 `ldr`） |
| `Poke32` | 写一个 32 位字（实现就是一条 `str`） |

它们注册在**事件过程表**里，而 `0x9052` 正是按名字查这张表 ⇒ **在 R1 上，`Peek32` / `Poke32` 可以经 USB 直接读写任意 RAM。**

### 2.3 能力与风险是同一件事 `[V]`

这两个 handler **没有任何对齐、范围或只读检查**。后果：

- 读一个未映射地址 → 可能 fault 在 PTP 任务里；
- **写一个未映射地址 → PTP 任务直接卡死**：相机界面还在，但 USB 不再响应，只能断电。

> 本项目实测踩过这条：写完未映射地址后几秒内 `WPD HRESULT 2147942833`，之后一切 USB 操作失效。
>
> **这也是为什么本项目不公开可执行的 `Poke` 命令。** 它不是"危险操作"，它是"一步走错就要拔电池"。

## 3. FAEXE 加载器

### 3.1 两条输入路径 `[V]`

`InitializeAdjustmentSystem` → 加载器：

```
读初始化位（RAM 里的一个 32 位字）
    非 0 → 立即返回 0，什么都不做（新字节不会被执行）
初始化载荷解码器（种子由固件内部提供）
分配 / 挂接一块约 1 MB 的可执行 RAM（0x44780000 一带）
查命名区 "FAEXE" 的 {base, size}
if [base] == 0 → 卡路径：先 A:/faexe.bin，再 B:/faexe.bin，读入后解码
else            → USB 路径：模块已由 0x905A 写进程序区，直接解码
blr base                        ← 执行，入口 = 文件偏移 0
从程序区末尾的固定槽取回调地址 → blr 它
if (w0 & 1) == 0 → 置初始化位 = 1
```

要点（都是概念级）：

- 载荷是**平坦二进制**，偏移 0 = 入口，**没有节加载、没有自动重定位**；
- 回调槽在程序区末尾附近的一个固定偏移处（具体偏移不在公开版）；
- 槽里若是 0，loader **不特判**，会直接 `blr 0` ⇒ 取指异常。

### 3.2 回调的参数 `[V]`

loader 调用回调时传两个参数：`x0` = 一个固件提供的注册函数，`x1` = 一个 loader 刚清零并填入内容的**接口块**（不是程序区末尾的回调槽）。

> ⚠️ 这里有一个**被外部复核抓到的错误**：早期文档写"回调 `x1 = base + 程序区末尾偏移`"，是错的。逐指令追踪显示 `x19` 在那个位置已经被改成接口块地址，随后 `mov x1, x19`。复核者独立按字节复核了这一条，结论一致。
>
> 这个错误本身不会让载荷当场崩（当时的新载荷没有依赖 `x1`），但它会误导后续的接口设计——**这正是"复核"存在的意义**。

回调的返回值 `w0` **原样**成为工厂命令的返回参数：

- `w0 & 1 == 0` → loader 置初始化位；
- `w0 & 1 == 1` → **不置位**。

⇒ **这给了我们一个干净的实验设计**：同一个载荷，只改回调返回值，就能得到"阳性/阴性"两组对照，且两组都证明"我们的代码跑了"。

### 3.3 实机验证 `[V]`

| 路径 | 步骤 | 观测 |
|---|---|---|
| USB（阴性） | `Allocate` → 上传 → `InitializeAdjustmentSystem` | 返回 `[1]`（= 回调返回值）；`IsAdjustmentSystem` 保持 `[0]` |
| USB（阳性） | 同上，回调返回 0 | 返回 `[0]`；`IsAdjustmentSystem` 变 `[1]` |
| **卡（阴性）** | 卡在槽 2，根目录 `faexe.bin`；**完全不发上传命令** | 返回 `[1]`；`IsAdjustmentSystem` 保持 `[0]` |

三条都带 identity 复查与终止包，会话正常结束。

⇒ **卡根 `faexe.bin` 被读取、解码、执行，回调返回值原样传回。** 这是 R1 上第一次实机确认"卡上自有 AArch64 代码执行"，全程只动 RAM 程序区：没有写 flash、没有写校准、没有改 BootDisk、没有写工厂标志。

### 3.4 重复运行与复位：必须带条件说

上一稿把这条写成了"一次开机只能跑一次"，**省略了前提条件**，是错的。正确语义（`[V]`）：

| 条件 | 行为 |
|---|---|
| 初始化位 **非 0** | 每次 `InitializeAdjustmentSystem` 立即返回 0、什么都不做；**新上传的字节不会被执行** |
| 初始化位 **为 0** | 每次都会重新"查命名区 → 拷贝 → 解码 → 执行 → 回调"，**可以反复跑** |

而"初始化位什么时候为 0"取决于**上一次回调的返回值**：

- 回调返回**奇数**（bit0=1）⇒ loader 直接返回，**不写初始化位** ⇒ 仍为 0 ⇒ 下次还能跑；
- 回调返回**偶数**（bit0=0）⇒ 置位 = 1 ⇒ 之后被门控挡住。

还有一个必须一起说的约束：**解码是原地的**。同一份编码字节被第二次"解码"等于再减一次 key ⇒ 代码变垃圾。所以即使门控为 0、能重复跑，**每次 `Initialize` 之前也必须重新上传**（`[V]` 原地解码 / `[I]` 因此必须重传）。

**三个可用的复位路径**（初始化位在 RAM 里，断电即恢复 0）：

| 路径 | 做法 | 风险 |
|---|---|---|
| **A（推荐）** | 让回调永远返回奇数 ⇒ 从头到尾不置位 | **只表示"不置初始化位"**；它不降低载荷本身的风险（挂死、Err70、写坏内存都照旧）。`IsAdjustmentSystem` 一直是 0 |
| **B** | 用 `Poke32` 把初始化位写 0 | 需要 Peek/Poke 通；只写 4 B RAM，最干净 |
| **C（不推荐）** | 调 `TerminateAdjustmentSystem` | 见 §3.5：**三条分支的结果完全不同** |

### 3.5 `TerminateAdjustmentSystem`：三条分支，别混着说 `[V]`

上一稿把这条写成"它无条件释放程序区、留下悬垂指针"，又把实机的 `0x17` 观测和悬垂风险连在一起——**是错的**。这个函数有三条互斥分支，只有第三条才走到释放：

| # | 进入条件 | 执行到哪 | 结果 |
|---|---|---|---|
| ① | 初始化位 = 0 **或** 工作区指针 = 0 | 在函数前段**直接返回** | 返回 `0x17`；**不释放任何内存**，也**不清位** |
| ② | 工作区释放**失败** | 释放工作区那一步返回错误码 | **不清位**；**没有**走到释放程序区 |
| ③ | 前置满足且工作区释放成功 | 释放工作区 → 释放程序区 → **清初始化位** | **位被清掉了**；但**不注销**命名区 "FAEXE" ⇒ 命名区指向已释放内存（悬垂），下一次上传会写进已释放内存 |

**本次实机观测到的是 ①**：阳性对照之后调用它，返回 `0x17`、`IsAdjustmentSystem` 仍为 1。原因是**从没调用过"分配工作区"**，所以工作区指针是 0，在函数前段就早退了。

⇒ 所以两句话都要改：

- ❌ "它不清标志"——**不成立**。走到 ③ 是会清的（需要先分配工作区）。`[V]`（代码）/ 未上机验证；
- ❌ "它会释放程序区并留下悬垂"——**只在 ③ 成立**，而且它和实机那次 `0x17` **没有关系**。

**正确的用法结论**：**别指望它做复位**——不是因为它"一定清不掉"，而是因为它的前置条件在实机路径上通常不满足，而满足时又会留下悬垂命名区。**断电重启是最稳的复位方式。**

## 4. 载荷要遵守的规则（这是本项目付过学费的地方）

| # | 规则 | 代价 |
|---|---|---|
| 1 | **保存并恢复所有 callee-saved 寄存器**（x19–x29） | 早期版本只存了 LR，直接成为 Err70 的元凶之一 |
| 2 | 栈必须有效且 16 B 对齐 | 同上 |
| 3 | 跳板覆盖的指令必须**逐字回放**（构建时从固件读出，不要重新编码） | 重新编码容易改掉条件码/立即数 |
| 4 | 回跳点必须精确（覆盖了 N 条就回到入口 + 4N） | 差 4 字节 = 崩 |
| 5 | 写日志区要放在**我们自己的可执行 RAM**，不要用相机自己的活数据区 | 实测那块低地址区被相机当作活数据使用，写进去会污染状态 |
| 6 | 页表重映射的补丁必须能被**重复运行**（先把描述符恢复成原厂值，再打） | 否则第二次运行会基于上一次的脏状态 |

关于第 1 条，外部复核的措辞值得抄下来：

> "loader 自己的保存不能替代载荷保存。loader 的帧保存了 x19/x20/x21/x22/x29/x30，却没有保存 x23–x28。"
> "把'回调单独算完并 ret'当成完整验证不够，必须验证返回 loader、再返回外层调用者后，所有应保存寄存器和 SP 均保持。"

## 5. 这条线的限制与边界

| # | 限制 | 等级 |
|---|---|---|
| 1 | **触发者是工厂命名命令，不是冷启动自动执行** | `[V]` |
| 2 | 初始化位置位后，后续 `Initialize` 被门控；复位方式见 §3.4 | `[V]` |
| 3 | `Terminate` 的清位有前提，且会留下悬垂命名区 | `[V]` |
| 4 | 程序区约 1 MB，超出会失败 | `[V]` |
| 5 | 载荷的**编解码密钥与算法**本项目不公开 | —（刻意） |
| 6 | 上传命令的**报文格式**本项目不公开 | —（刻意） |
| 7 | 是否能与卡启动桥"在同一次开机里都跑"**未系统验证** | `[?]` |

> 第 7 条在实践上其实已经发生过：卡启动桥本身就是"页表重映射 + 跳板 + 桩"的组合，而跳板与桩的构建器与 USB 路线共用。但"两条路在同一次开机里都跑"这个组合**没有单独测过**。

## 6. 与卡启动的关系

一句话：**FAEXE 让你"随时能跑"，卡启动让你"开机就跑"。**

实现最终功能（连拍节流）时，本项目两条路都用了：

- 开发阶段：USB + FAEXE，十分钟一轮，改参数快；
- 交付形态：卡启动桥，开机自动生效，不需要插线。

两者打的是**同一个补丁**，落在**同一批页**上——这也是为什么 [02](02-cardboot.md) 里那个 wrapper 做的事，和 USB 路线里的重映射模块几乎逐条对应。
