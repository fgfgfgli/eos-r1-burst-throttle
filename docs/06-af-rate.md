# 06 · 每秒 AF 检测次数

> 用户的问题：R1 的对焦检测能不能做到更快？
> 短答案：**我们在两个 4K 视频窗口里测到约 59.9 次/秒，与 60 fps 量级相符**；机制上它看起来由"每秒有多少个 DAF raw 帧"决定，`[I]`，而且**不能**由此推出"全模式严格等于 LV 帧率"或"软件上限已排除"。
>
> 公开版只到机制与证据等级；钩子落点、计数桩布局、页表槽位与变体机器码不在公开版。

---

## 1. 先搞清楚 AF 评估在哪跑

### 1.1 评估代码在子 CPU 上 `[V]`

连续 AF 的评估代码位于**子 CPU 的 DAFState 镜像**里：一段约 `0x3C700` B、**Thumb** 指令集的镜像，搬到一个固定低地址运行；**主 CPU 对它的引用为 0 处** `[V]`（有界扫描）。

⇒ 主核不直接跳进去跑。它通过**命令**驱动。

### 1.2 主核每帧发一条命令 `[V]`

主核每帧向 DAF 引擎发一条 `DafrawCmp`（命令号 7），然后同步等待结果。

全镜像里这条命令的发送器**只有一个**：它的包装函数的唯一调用者就在它内部，而它在镜像里**唯一的静态指针**落在一张 rodata 表的第 7 项（与命令号 7 对齐）——**而那张表没有任何代码引用**（`ADRP+ADD` / `LDR` / 字面量 / 裸指针全 0 命中）`[V]`。

⇒ 调用方是**间接派发**，静态给不出调用者地址。这也是为什么补丁策略只能是"钩函数本体"而不是"钩某个调用点"。

> 具体地址不在公开版：**"唯一发送点"这个结构结论**才是要点，知道它在哪个 VA 只是重建的门槛。

### 1.3 DAF 引擎是帧驱动，不是定时器驱动 `[I]`

从状态机形状看（`WAIT_DAFRAW` / `DAFRAW_CMP` / `IsBufferInProcess` + ping-pong 缓冲 + 同步等待 + 超时分支），它以**帧缓冲/事件**推进：每送来一个 DAF raw 帧，评估一次。

但**"没有独立定时器"这个否定命题本轮并没有证死** `[?]`：我们只在 DAF 命令族与 AF 决策层做了**有界扫描**，没有找到"每 N 帧一次"或"帧计数 % N"的分频结构。

⇒ 所以"每秒几次"更可能是**结果**（每秒有多少 raw 帧），而不是固件里的一个可调参数。这是 `[I]`，不是 `[V]`。

## 2. 把它测出来

### 2.1 探针设计 `[V]`

在命令发送器入口装跳板 → 桩：每次进入时计数器 +1、记录 `CNTVCT_EL0`；逐字**回放**被覆盖的原 prologue 指令（构建时从固件读出，不重新编码）；回跳。

同时挂了另外两个点：CAP→SensorMode getter 与 DS class 选择器，用来交叉判断当前状态。

> 踩坑一：第一版把日志区放在相机自己的活数据区（低地址一块），装的时候读到那里有像指针的大值。后来把日志移到我们自己的可执行 RAM。
>
> 踩坑二：装好后**计数器不动**，一开始被误判成"补丁没生效"。其实只是相机在空闲（USB 连接态 / 待机 / 取景关闭 / AF 未激活）。用 PTP 触发一次 release 之后，计数立刻开始增长 `[V]`。

### 2.2 实测结果 `[V]`（两个窗口，仅此而已）

相机停在 **4K 视频档**、无人工操作：

| 窗口 | Δcmd7 | ΔCNTVCT | 时长 | cmd7 / 秒 | cap 查询 / 秒 |
|---|---|---|---|---|---|
| 20:17:40.8 → 20:17:46.0 | 312 | 5,205,196 | 5.206 s | **59.93** | 299.7 |
| 20:18:04.8 → 20:18:10.0 | 312 | 5,221,890 | 5.210 s | **59.88** | 300.2 |

同时确认：

- `CNTVCT_EL0` 实测 ≈ **1.000 MHz**（5.21 s ↔ 5.21e6 ticks）⇒ RAM 里的时间戳可以直接当微秒用 `[V]`；
- 同期状态：行模式全局 = **2**、DAFCaptureMode = **0**、最后查询的 cap = **10**、DS 选择器计数 = 0。

### 2.3 这两个数字能说明什么、不能说明什么

**能** `[V]`：

- 在**这两个 4K 视频窗口**里，每秒 `cmd7` 次数约 **59.9**；
- 与 60 fps 的**相对差**约为 **0.115%** 与 **0.192%**；两个窗口之间的相对差约 **0.077%**；
- 两个窗口都是 312 次，重复性很好。

**不能**（上一稿在这里写过头了，本稿收回）：

- ❌ "**全模式**严格等于 LV 帧率"——只测了 4K 视频档的两个窗口；4K 120p、30p、6K 60p、拍照伺服 AF **都没测**；
- ❌ "**不存在**独立定时器"/"软件上限已排除"——只做了有界扫描，源记录明确写着"不能声称固件里不存在"；
- ❌ "误差在 0.1% 以内"——这句话没写清比较对象。按 60 fps 算，两个窗口分别是 0.115% 与 0.192%，**并不都在 0.1% 以内**。

## 3. 机制：一个"三者取最小"的模型 `[I]`

从四条独立证据（状态机形状、命令族无分频结构、窗口高度参与单帧耗时、读出由三元组选定）合成出来的模型是：

> 每秒检测次数 ≈ **min（传感器 DAF raw 帧产出率，DEFUSER 处理率，主 CPU 同步往返率）**
> 其中第一项由读出模式/时序决定。

这是 `[I]`，**没有实测**。

**这个模型本身也有漏洞，必须说清**：它是"三项取最小"的形状，但本项目**并没有逐项排除**其它可能的瓶颈——例如：

- 三项各自的**实际数值**都没测（我们只测了"结果"= cmd7 次数，没测三项分别多少）；
- 主核同步往返率与引擎处理率**谁先饱和**没有分离实验；
- 是否还有**第四项**（总线/中断延迟、状态机轮询粒度）完全没有查 `[?]`；
- 存在一个"软件上限"的可能性**也没有排除** `[?]`（见 §7 第 5 条）。

⇒ 所以它只能当**工作假设**用：它解释了"为什么改行模式不像提频"，但**不能**用来预言"提高某一项就一定能提频"。

⇒ 目前能说的只是：**提高 LV / 传感器读出帧率是候选路径之一**；改行模式是"换档"（改每次读出的行数 / 共享方式），**可能改变单帧耗时而非每秒次数** `[I]`。

## 4. "行模式"是干什么的

这是本项目花时间最多、也最容易误解的地方。

### 4.1 那个全局只有一个读者和一个写者 `[V]`

早期文档说这个全局"被很多地方读"。**错。** 全镜像扫描：**读**只有包装函数自己（用来判断"行模式是否变化"），**写**只有一处。

那 10 个地址是**判定函数的调用点**，不是这个全局的引用点。这两件事被混为一谈过很久。

### 4.2 真正的消费者只有 3 个 `[V]`

10 个调用点里，只有 3 个把 1/2 作为参数喂给 **DAF capture-mode 选择器**；输出写进全局 DAFCaptureMode 与 capture 参数块。其余 7 个只是把值存进状态块。

### 4.3 1 和 2 差在哪 `[V]`

```
if (MvDafCaptureMode(LvCapMode, DafMode) == 2 && lineMode == 1)
    → 走 "MultiStream" 分支，DAFCaptureMode = 0
else
    → DAFCaptureMode = MvDafCaptureMode（查一张 84 项的表）
```

**方向是 `[I]`**：`1` = MultiStream 精简档（更快/更省），`2` = 专用全量 DAF 档（更慢/更准）。

> 这一条**只有实机能定**。所以测量桩不是"顺手做的"，它是**判决实验**的一部分。

### 4.4 谁会返回 2 `[V]`

按 ROM 控制流精确复刻判定函数：**在 cameraMode 0..120 里，只有 25 个值可能返回 2**（正好是视频/多流档的一批取值）；其余全部恒返回 1（顶层就返回）。

当前拍照 LV 读到 1 ⇒ 与"cm ≤ 5 恒 1"或"掩码位为 0 恒 1"都相容 ⇒ **拍照档在自然状态下不在可返回 2 的集合里**。

## 5. 提频补丁：设计好了，没上机 `[?]`——而且风险比上一稿写的大

### 5.1 两种改法，风险完全不同

| 变体 | 改法 | 影响范围 | 风险 |
|---|---|---|---|
| **全函数替换**（force2 / force1） | 把判定函数换成 `mov w0,#2; ret` | **任何 cameraMode 都变成 2** | **拍照档也会被强行改成 2** |
| **条件修改**（掩码） | 只改视频/多流档的"是否进 deep"掩码 | 只影响视频/多流档 | 改错会把非视频档也拉进 deep |

> ⚠️ **上一稿写错了一句**：从"拍照档自然状态下返回 1"推出"所以改它对拍照行为不变"。
> 这两件事**不是一回事**：全函数替换会把拍照档**也**改成 2。源记录（`AF-RATE-R1.md` §3.3）明确写着"V1 会把拍照档也强行改成 2，这是最大的风险来源"。
> 本稿已更正，并且——因为**两个变体都没上机**——**不宣布任何"行为不变"**。

### 5.2 为什么没做

三个原因，按重要性：

1. **它是"换档"不是"提频"**（§3）。判定函数**只在 capture setup / 模式重配时被调用**，不在每帧路径上。改了它，得到的可能是"更准但更慢"或"更快但更糊"，而不是"更多次"。
2. **最可能的提频路径是 LV / 传感器读出**（候选，不是已证结论）：§3 的三项取最小模型把"每秒 raw 帧数"放在第一位，但三项的实际数值都没测，其它瓶颈也没排除。那条链还与 6K 全高**共用**，两项必须一起评估。
3. **风险不清**：副作用（SNR、画质、发热、与 6K30 的冲突）完全未知，而它要动的是**实时对焦路径**；全函数替换还会污染拍照档。

### 5.3 如果要做，实验矩阵应该是什么样

| 变体 | 改动 | 要测什么 |
|---|---|---|
| E0 | 无（对照） | 拍照 LV 的 Hz 基线 |
| E2 | 探针 + 恒 2 | Hz、行模式全局、DAFCaptureMode、**拍照是否还能合焦** |
| E3 | 探针 + 恒 1 | 同上反向 |
| E4 | 探针（视频档，不改变体） | 视频档自然值 |
| E6 | 探针 + 掩码 0 | 掩码路径验证 |

每组 ≥30 s，每次只改一个变量，并且**必须同时记录行模式全局**——否则无法判断"是真的没变，还是补丁没生效"。另外：判定函数只在 capture setup 时被调用，打完**必须触发一次重配**（半按 AF-ON / 切对焦模式 / 进出录制），否则会被误判成"补丁没生效"。

## 6. 页表冲突（动手前必读）

AF 计数桩与 6K 谓词补丁落在**同一个 2 MB 块**（同一个 L2 槽）；AF 行模式补丁与卡启动桥 + 连拍节流落在**另一个同一个块**。

- 默认 `merge` 模式：复用既有 L3，两者共存；
- `--replace-l2`：**会顶掉先装的那个**，而且**静默失效**（不报错）。

> 两条块级结论：**AF 与 6K 同块；AF 行模式与节流同块。** 同块必须共用 L3。两个补丁模块彼此不冲突（不同块），可以先后跑。

**回滚**：全部 RAM-only，断电即恢复；运行中撤销 = 跑一次 `--noop` 变体或断电。

## 7. 未建立的部分 `[?]`

诚实清单（这些都是"没做到"，不是"不存在"）：

| # | 未建立 | 影响 |
|---|---|---|
| 1 | 每秒次数的**真正绑定点**（min 模型是 `[I]`，无实测） | 无法确定"提高哪一项才有效" |
| 2 | 命令的**每帧触发者**（间接派发，静态给不出函数地址） | 无法从上游改频率 |
| 3 | 行模式 1/2 与**传感器寄存器**的直接对应（没找到写点） | 改了行模式不知道硬件上发生了什么 |
| 4 | 几组状态字段的下游读者 | 无法判断改动的连锁反应 |
| 5 | **是否存在软件层面的每秒上限** | 只做了有界扫描，**不能声称不存在** |
| 6 | DAFState（Thumb）镜像的入口与函数边界 | 评估函数入口给不出来 |
| 7 | 那张 rodata 表为何无引用 | 可能被启动期拷到 RAM，或被外部/调试路径使用 |
| 8 | **提频补丁的实际效果** | 没上机；全函数替换还会改拍照档 |

## 8. 一句话总结

> **在两次 4K 采样窗口内测得约 59.9 次/秒，与 LV 帧率同量级；全模式是否严格相等未证。**
> 机制（三项取最小）是 `[I]`，软件上限是 `[?]`，提频补丁没上机。
