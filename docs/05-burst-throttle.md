# 05 · 连拍降速与节流

> 用户的原话是"**卡启动 r1 连拍降速不停**"。
> 这一项**做成了**——但它不是"改一个数字"，中间有三轮失败，而且最后的方案跟最初的设想完全相反。
>
> 公开版只到机制与证据等级；跳板/桩布局、落点地址、写入常量与页表槽位不在公开版。

---

## 1. 连拍的"停"到底是谁决定的

### 1.1 唯一的判决函数 `[V]`

"要不要发起下一帧"**只有一个地方**决定：规则求值函数（`RuleEval`）。全镜像只有两条 `BL` 调它，而这两个 handler **本身没有任何调用者**——它们只能由状态机表的槽位触发。

### 1.2 返回值不是 bool，是规则号 `[V]`

规则求值写两个输出：规则号与 immediate 标志。规则号经释放请求分发点**一对一**翻译成事件号：

| 规则号 | 事件 | 语义 |
|---|---|---|
| 0 | ev18 | **真正发起下一帧** |
| 1 | ev19 | Suspend（挂起） |
| 2 | ev20 | Standby（待机） |
| 3 | ev21 | 暂停 |
| 4 | ev3 | 释放结束 |

**只有规则 0 会走到"发起下一帧"。** 其余四个只设状态字 + 装场景定时器，从不发"开始"事件。

### 1.3 四个闸门 `[V]`

规则求值依次试 4 个谓词，命中即返回。其中两个与"要不要停"直接相关：

- **Standby 谓词**：驱动模式字段 == 7
- **Suspend 谓词**：驱动模式字段 ∈ {1,4,5,8,0x12,0x14,0x15,0x16}

两者互斥，所以"Standby 先于 Suspend 被测试"这个顺序**实际不起作用**。

> `G` 不是常量地址，而是从一个固定 RAM 槽里取出的结构指针。所有 `G[0x…]` 的读取都是"取指针 → 加偏移 → 读字节"。这一点在追字段时**必须记住**，否则会去扫一个不存在的常量地址。

### 1.4 唯一的"配额"比较 `[V]`

整条链里只有**一处**配额比较：一个**每帧 +1 的帧计数**与一个由两个字节字段算出的阈值比较（同一条件在两处出现）。
它**不是缓冲深度，也不是写卡状态**。

### 1.5 于是有一个负结论——但必须带边界 `[V]`/`[?]`

> `[V]` 在规则求值函数的 **13 个直接依赖** + 检查函数的 **14 个直接被调**范围内，**没有一个是 media / CF / SD / 写入队列 API**。
>
> `[?]` **多跳没有排除**：job 层完全可能把某个字段写成"卡忙"，再由本链读到。本轮**没有逐个追**其余闸门字段的写者——这正是"有没有某处把卡状态塞进这些位"的唯一可能入口。

⇒ 可以说的是：**"改这条链"不会带来"写卡时继续拍"的输入**。
**不能**说的是：这条链不可能受到卡状态影响。上一稿写成了后者，本稿已收回（复核意见 R5 第 ① 点）。

## 2. 第一层误解：那两个大数字是什么

Suspend / Standby 的动作体做两件事：把状态字置 4，然后挂一个**大数值的定时器**（3000 / 80000）。

**注意措辞**：这里**不能**写"定时到才继续"——那正是下一句要否定的误读。准确的说法是："它同时挂了一个 3000/80000 的定时器，而超时回调会记录 `TimeOut` 并断言。"那到底有多少"等"的成分，本轮没定论 `[?]`。

**最初的误读**：这是"重试间隔"，缩短它就能更快恢复。

**外部复核的更正 `[V]`**：这是**场景超时上限**，不是"等够了才重试"。超时回调会记录 `TimeOut` 并断言。那个 `×48` 是步骤索引。

这个更正很重要——但它**没有**解释后面全部现象，见 §2.1。

### 2.1 三组实验（把"缩短延时"这条线走到底）

| 实验 | 改动 | 预期（错的） | 实际 |
|---|---|---|---|
| E1 | 3000 → **500 ms** | 恢复变快 | "停，但接上的快"——**恢复确实变快了**，但仍会停 |
| E2 | 3000 → **50 ms**（≈20 fps 轮询） | 更平滑 | 缓冲满瞬间 **Err70** |
| E3 | 把"配额挂起/释放结束"两处分支改成无条件跳转 | 不再停 | **仍然会停** |

E3 是决定性的：**把配额逻辑整个短路掉，相机照样停。** ⇒ 配额规则不是那个闸。

> ⚠️ 一处**仍未闭合**的矛盾（复核意见 R5 第 ⑥ 点）：如果那 3000/80000 纯粹是"场景超时上限"，为什么 E1 把 3000 改成 500 之后**恢复确实变快了**？两种可能：①主核自己也在用这个值当重试间隔（双重语义）；②E1 改变的是别的时序。**本轮没有定论** `[?]`。
> 所以本稿把"300 ms / 500 ms 之后恢复"一律写成**观测**，不写成"机制保证"。

## 3. 第二层：真正的原因是缓冲写满 `[V]`

用"在挂起入口埋日志"测到：**挂起瞬间前端缓冲剩余空位 = 3**，满容量 **40**。

⇒ 在这组观测里，连拍的"停"是**前端缓冲写满**造成的，不是帧数配额。帧计数那条只是同一现象的另一面。

补充事实：前端缓冲剩余由 MEMCOND 维护（有专门的写入日志点），而**释放链从来不读它** `[V]`（有界：指我们检查过的调用面）。

这解释了一个悖论：**缓冲水位明明是可读的，但释放决策不看它。** 这正是"降速继续"要自己动手的原因。

> 边界：这是**一次**挂起瞬间的采样值（3/40）。它可以支持"停与缓冲写满同时发生"，但不构成"停的唯一原因"的证明。

## 4. 第三层：自旋方案，以及它为什么必须放弃

### 4.1 v4 的思路 `[V]`

在"每次继续拍的唯一入口"装跳板 → 桩：规则 0 且前端缓冲空位低于阈值时，**自旋延时**（按空位线性计算，上限约 52ms，≈19fps）；空位充足时完全不拦。同时把挂起重试改到 500 ms。

**实机结果**：H+ 按住 12 秒 ⇒「降速 → 短暂 busy → 又继续」循环，**不再长时间卡死**。用户确认可用。

### 4.2 但自旋有两个致命问题

**问题一：一个自指的死代码 `[V]`**

v5 加了一个"封顶到上一帧间隔"的保护。实际上：时间戳**只在节流分支里**写，于是"上一帧间隔" = 上次被节流调用到现在 = **帧周期 + 上一次自旋**，恒大于本次想自旋的值 ⇒ `min(desired, interval)` 几乎**永远取 desired**。

**这个"保护"从来没生效过。** 40fps 下空位被打到 3，按当时参数算出的目标值远超安全线。

**问题二：AF-ON 快速切档是更严的约束 `[V]`**

| 每次自旋上限 | 结果 |
|---|---|
| 15 ms | 不崩 |
| 25 ms | 不崩 |
| 35 ms | 不崩（测不出） |
| **40 ms** | **Err70** |
| 126 ms | Err70 |

触发条件是：**AF-ON 二段半按 + 连拍**交替按。这是真实使用中最常见的动作，所以"35ms 安全"没有实用价值——**它只是在测试里碰不到而已**。

> `[?]` 补充：后来哪怕 15–35ms 的自旋，叠加"AF-ON + 快门"反复按也会**偶发** Err70。所以本项实际的红线是"**不要阻塞这条路径**"，而不是某个具体的毫秒数。

### 4.3 为什么"可中断自旋"物理上不可能 `[V]`

想法很自然：自旋时不停检查"驱动模式是否变了"，变了就提前退出。

**做不到。** 理由：驱动模式字段的**唯一写点**在参数更新里，而派生字段只在规则求值/参数更新时生成 ⇒ **在自旋窗口内读到的永远是"结果"，不是"请求"**。参数更新根本不会在你自旋的时候发生。

### 4.4 硬时限在哪：本次能看到的范围 `[V]`（有界）/ `[?]`（全称）

**`[V]`（有界）**：在本链涉及的 scene timeout 里，**没有观察到** 50–100ms 级的值——全部 ≥ 2500ms，挂起/待机是 3000/80000ms，定时器单位是**毫秒**。

**`[?]`**：这**不能**推出"状态机层绝对没有这么短的超时"。我们只做了"本链涉及的定时器"这个范围的扫描；别的模块、别的任务、以及**不经过定时器对象**的等待（忙等、锁、事件标志）都不在这个结论里。

在**本次能观察到的**材料中，与帧节拍同步的硬时限出现在传感器/曝光层：

| 断言 / 错误 | 含义 |
|---|---|
| `SR ExposureStartTiming(Syngen1) is overrun` | 计划曝光时刻 + delta 已过 |
| `ExecAccumH over VdSize` | 累加行数超过 VD |
| `[SLCP] AccumH is less than min-VD` | 累加行数不足 |
| `HEAD ERROR >>> BUFFER FULL` | 缓冲满错误 |

**窗口 = 当前模式的 VD**：20 fps ≈ 50 ms，40 fps ≈ 25 ms。

⇒ 这**可以**解释"为什么挡住这条路径会撞断言"，但**不能**解释成"硬时限只存在于这一层"。两条都必须写清：

1. **具体哪一条断言先触发，本轮没有捕获到** `[?]`——把四个候选名字列出来，不等于定位了失败链（复核意见 F38）；
2. **这四条断言属于"连拍自旋"这条实验线**，与 6K OpenGate 那条线定位到的 `ImageSequence…:1748` 是**两回事**（见 [07](07-open-gate-err70.md) §8）。

## 5. 最终方案：不自旋，改写结论

### 5.1 思路 `[V]`

不去"等"，而是**把相机的结论改掉**：规则 0（继续拍）且前端缓冲空位低于阈值时，把结论改成规则 1（Suspend）。

打开这条路径后，相机**自己**去执行挂起：设状态、挂场景定时器、完成回调 → 恢复检查 → 恢复。

**全程非阻塞，不阻塞任何任务**，与"缓冲满时相机自己进入 Suspend"**同构**。

配合把挂起/待机的重试数值改小，就是"停一下再继续"。

### 5.2 定稿参数（研究记录，不是操作指引）

| 项 | 值 |
|---|---|
| 触发水位 `FREE_THRESHOLD` | **12**（前端缓冲空位 < 12 就把规则 0 改成 1） |
| 挂起恢复 | **300 ms**（由 3000 改小而来） |
| 机制 | 非阻塞：复用相机自己的挂起路径 |
| 额外要求 | 桩内必须保存/恢复 x18–x21（被调用者保存寄存器） |

### 5.3 实机结果 `[V]`（观测）

> 40 张拍满 → 「拍一阵 → 停一下 → 再拍一阵」循环；
> 写卡/停顿期间**反复按 AF-ON + 快门不崩**；用户确认可用。
> 平均等效约 **15–20 fps**。

后来又通过卡启动桥在冷启动下复核：**不崩、降速生效**（幅度受卡写速限制）。

> ⚠️ 这些是**现象记录**。它们**不构成**"300 ms 必然恢复"或"50 ms 必然崩"的机制保证：
> - 300 ms 是选定的参数，配合"更频繁但更短"的手感，**不是**测出来的最优解；
> - 50 ms 崩是**一次**观测（E2），后来没有做 50–300 ms 的逐点扫；
> - 二者在原始材料里与"场景超时上限"的语义**仍有冲突**（§2.1）。

### 5.4 调参手感（实测）

| 水位 / 恢复 | 体感 | 结果 |
|---|---|---|
| 8 / 500 ms | 停顿早、次数少 | 认可 |
| 6 / 500 ms | 停顿更晚更少 | 可用 |
| **12 / 300 ms** | **更频繁但更短** | **选定** |
| 自旋 40 ms（任何参数） | — | 叠按键活动偶发 Err70，弃用 |

**调参入口只有两个**：水位（调低 = 停顿更少但更长；调高 = 更频繁但更短）与恢复时间。

## 6. 这条线的边界

| # | 边界 | 等级 |
|---|---|---|
| 1 | **这不是平滑降速**，是"停一下再继续"。体感是顿挫，不是索/尼式的连续降速 | `[V]` |
| 2 | 等效平均帧率约 15–20 fps，取决于卡写速 | `[V]` |
| 3 | RAM-only：换卡/断电后补丁丢失，需重打；走卡启动桥则开机自动重打（前提是 BootDisk 仍开着） | `[V]` |
| 4 | 任何自旋方案在"AF-ON 快速切档 + 连拍"下都有 Err70 风险，**不要因为 35ms 测不出就以为安全** | `[V]` |
| 5 | 原厂（无补丁）在同样操作下是"正常 busy、不崩" ⇒ 崩是**我们的补丁**引入的，不是相机固有问题 | `[V]` |
| 6 | 准入链的直接调用面里没有卡/写卡输入 ⇒ 真正"边写边拍"需要作业层/写卡等待那条链上的常驻策略，属热路径注入的大工程；**间接状态输入未排除** | `[V]`（有界）/ `[?]`（间接） |
| 7 | 300 ms 恢复是选定参数 + 观测，不是机制保证；E2 的 50 ms 崩溃是单次观测 | `[V]`（观测）/ `[?]`（机制） |

## 7. 一个不碰固件的替代方案

如果目标只是"连拍时手动控速"，相机**自带**这个能力：

> R1 的 AF-ON 是二段式按钮，可以在菜单里设成「半按 = 切换/提高连拍驱动档」。用实体按键手动控速。

**优点**：不碰固件 ⇒ 没有 Err70 风险、没有预拍摄回归风险、没有保修问题。
**缺点**：要人手按，不能自动化。

对绝大多数拍摄场景，这是更理性的选择。**本项目做固件方案的价值在"研究"，不在"实用"。**

## 8. 复盘：三轮失败教会了什么

| 轮次 | 错在哪 | 教训 |
|---|---|---|
| E2 | 把"场景超时上限"当成"重试间隔" | 改小超时不会让重试变快，只会让它更早超时（但 E1 又显示"恢复变快"——语义仍有 `[?]`） |
| E3 | 以为"停"是配额规则造成的 | 短路掉配额逻辑后照样停 ⇒ **闸不在那里** |
| v5 | "封顶"逻辑自指，从未生效 | **保护性代码必须能被证明生效**（打日志/回读），否则它只是安慰 |
| v10 | 以为"35ms 安全" | 安全边界取决于**测试场景**；要测最坏场景（按键 + 连拍交替） |
| v14 | —— | **与其和调度器抢时间，不如把结论改掉**：让相机自己走它自己的挂起路径 |

最后一条是这次的核心洞察：**不要自己实现节流，要复用固件已有的节流机制。** 它已经处理好了所有你不知道的时序约束。
