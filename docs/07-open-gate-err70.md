# 07 · 6K OpenGate 与 Err70

> **Credit / 署名**：Canon EOS R1 research by **fgfgfgli** — 基于本文做新机型研究时，请注明作者并附仓库链接（CC BY-NC 4.0）。 / If you build on this, credit the author and link <https://github.com/fgfgfgli/eos-r1-firmware-research>.


> 目标：让 6K RAW 视频录出 **3:2 全高（约 6000×4000）**，而不是现在的 17:9（6000×3164）。
> 结果：**没有做成。** 但根因被收窄到一条具体的断言上，这是本轮最接近答案的结论。
>
> 公开版只到机制与证据等级；表项地址、谓词地址、运行时副本地址、探针与桩布局不在公开版。

## 1. 现状：为什么是 3164 而不是 4000

### 1.1 6K RAW 用的 cap 是 55，不是 54 `[V]`

早期文档一直假设"R1 的 6K RAW 槽 = CAP[54]"（因为同平台机型是 54）。**这个假设是错的。**

用页表重映射在谓词里埋一条日志，把实参写到一块日志 RAM，然后拨到视频档：读到 **`0x37 = 55`**。

| cap | SensorMode | 几何 | 说明 |
|---|---|---|---|
| **CAP[55]** | **4** | `6208×3320` | **17:9** ⇒ 录出 6000×3164，与现状完全对上 |
| CAP[54] | 5 | `6208×6640`（= 2×3320） | 也是 17:9 类，**不是** 6K RAW 的槽 |

`[V]` 实测（日志读数）+ 静态核对（两张 CAP 表里都能对上）。

### 1.2 R1 里"全高"这条路径是被桩掉的 `[V]`

DS（down-scale / 分类）选择器有两个谓词：

| 谓词 | 行为 |
|---|---|
| 谓词 1 | 返回 1 ⟺ SensorMode ∈ **{2,3,5}** |
| 谓词 2 | **永远返回 0**（`mov w0,#0; ret`） |

⇒ **R1 的 DS 选择器只会返回 0 或 1；class 2 这条路径在固件里是死的。**

对比同平台机型：它的 class 2 谓词检查另一组 SensorMode，CAP54 命中 ⇒ 走 class 2（全高）。

**这解释了"R1 没有全高视频"的机理**：不是参数没调对，而是**这一层在固件里被禁用**。

> 边界：这只能说明"这一条分类路径不可达"，**不能**单独推出"全机不存在其它全高路径"（复核意见 F30 的限定）。

### 1.3 但 R1 固件里**存着** 3:2 全高的 profile `[V]`

在 DS profile 页里同时找到 3:2 全高与 17:9 两套记录：

| 记录 | 读出 | 作业 | 派生 |
|---|---|---|---|
| **3:2 全高** | `6160×4144` | `6032×4024` | 3144×2136 |
| 全高（另一变体） | `6160×4144` | — | 2532×1728 |
| 17:9 | `6160×3312` | `6032×3192` | 3144×1716 |

⇒ **几何数据是现成的**，缺的只是"让它被选中"和"让副核接受"。

## 2. 第一个尝试：直接改 SensorMode，结果 Err70

思路很直接：CAP[55] 的 SensorMode 从 **4**（`6208×3320`）改成 **1**（`6208×4160`，全高），再把 DS 谓词改成对该 cap 返回 class 2。

**实验矩阵（全部 RAM-only）：**

| 补丁 | 结果 |
|---|---|
| **noop**：只重映射页表，**一个值都不改** | ✅ **正常录像** |
| CAP[55] 4→1（只改传感器模式） | 拨到视频档 **Err70**（拔线/切档前正常） |
| CAP[55] 4→1 + 谓词对该 cap 返回 class 2 | **Err70** |
| 再加 DS 几何成套改（4144 / 4024 / 2136 / 4143…） | **Err70**（这次卡住时间更长） |
| CAP[54] 5→1 + 谓词对 cap 54 返回 2（早期，cap 认错） | 正常录制（仍是 3164） |

### 2.1 这些结果能说明什么

**能** `[V]`：在这一组配置与这几种变体下，**把 6K RAW 的 SensorMode 从 sm4 换成 sm1 就进不去视频模式**；改 class、改几何都没有改变这个结果（一个还让卡住时间变长，说明代码走得更深）。

**不能**（上一稿写过头，本稿收回）：

- ❌ "Err70 **与 class、几何无关**"——我们只试了"改"这几项，没试过"别的组合"；正确说法是**"已试的这些改动不足以让它通过"**；
- ❌ "noop 一次通过 ⇒ 重映射机制**普遍**安全"——它只证明**这一次**没引入故障（复核意见 R5 第 ④ 点）；
- ❌ 最后一行也提醒一件事：**cap 认错的时候实验会"通过"，但什么都没变。** 这是最危险的假阳性。

## 3. 一次关键的发现：副核有一份独立的运行时副本 `[V]`

### 3.1 之前所有实验都跑在不一致状态上

用 Peek 把副核的 CAP 表对上之后发现：副核的数据模块在 ROM 里有一份源，**装到 RAM 后另有一份运行时副本**，两者内容可以不同；而当时的构建器**只改 ROM 页，从未改过运行时副本**。

⇒ **之前所有「CAP[55] 4→1 + class2 + 几何」实验，实际状态都是"主表改了、副核运行时没改"（不一致）。**

这个变量此前从未被测过——它正是同平台公开研究里专门做"一次同步"的那一层。

> ⚠️ 为什么运行时副本会不同：装入器对镜像开头的**两个自指针**做了重定位（差值 `0xDD000`，注：上一稿误写为 `0xD000`，见 [01](01-evidence-and-method.md) §2.3 勘误），`+0x08` 起才逐字相同。所以"ROM 里改了就等于运行期改了"是错的。

### 3.2 E-OG1：第一次在"三处一致"的前提下测试

| # | 动作 | 结果 |
|---|---|---|
| 1 | 重映射：谓词对该 cap 返回真；主 CAP[55]=1；ROM 源第二份 CAP[55]=1 | `ok` |
| 2 | 写副核**运行时** CAP[55] ← 1 | — |
| 3 | **主核侧**回读核对 | 主表=1、谓词指令正确、ROM 源副本=1、运行时=1、CAP[54] 未动（仍是 5） |

其他一切未改：CAP[54] 两处都是 5；DS 几何页没碰；拍照路径不受影响。

**结果：仍然 Err70。** `[V]`

### 3.3 但"一致"这个词要打折扣 `[V]`/`[?]`

> `[V]` 我们在**主核**侧读回了三处都等于 1。
> `[?]` **这不等于 Xtensa 看到的也是 1**：副核跑在另一套总线上，**cache 可见性/一致性没有验证**。源记录明确保留了这一点（"Xtensa 实际可见性未验"）。

⇒ 正确说法是：**"在主核观测到三处一致"的前提下仍然 Err70**；
**不能**说"表不一致已被完全排除"（复核意见 F31 的限定）。

这一条有个实际后果：**"改运行时副本"这条路本身可能是无效的**（副核可能根本看不到主核的写），也可能有效但还缺别的条件——本轮无法区分。这是本条线最大的方法漏洞。

## 4. 把断言抓出来

### 4.1 装"吞断言"探针：Err70 变成黑屏 `[V]`

在统一断言入口装钩子，**只记录、不中断**（记录后直接返回）：

- 用户切到 6K RAW 视频档 → **黑屏（不是 Err70）**；
- 相机保持可枚举，USB 仍能读。

⇒ **吞掉断言成功阻止了死机**，说明失败确实是由断言驱动的。

抓到的日志：断言 file = 主核↔副核通信模块（`Festa::RadonComMainToRadon.c`）；命中 **25 次**（静态，不再增长）；**`RequestModeChange` 计数 = 0**（一次都没跑到传感器模式设置）；**DS 选择器按 cap 55 跑了 3 次**（⇒ CAP 表改动**确实生效了**）。

### 4.2 第二次探针：抓到失败分支 `[V]`

再钩通信助手，把它的调用方行号记下来：

| 项 | 值 | 含义 |
|---|---|---|
| 失败分支 | **`0x86`（134）** | "副核状态字 ≠ `0xACCEDFEE`"那条检查 |
| 助手被调用次数 | **1469** | 主核在重试循环里狂调（吞掉后就地重试） |
| 共享状态字 | **0**（期望 `0xACCEDFEE`） | 副核"就绪"魔数；整块区域全 0 |

**失败链（当时的证据闭环）**：

1. CAP[55]=1 生效，DS 选择器按 cap 55 跑过；
2. 主核进入副核同步路径，检查共享状态字是否 = 那个"就绪"魔数（全固件只有这个模块用它）；
3. 该字是 0 ⇒ 通信助手记 `Main Assert Line[134]` 并断言；吞掉断言后主核再次重试（1469 次）；
4. 于是主核永远等不到 ⇒ 黑屏（不吞断言时就是 Err70）。

**当时被排除的（现在仍成立）**：不是 DS class 缺失、不是主核"模式非法"断言（那个断言未触发）、不是主核 tune 表未初始化（两档指针都非空）。

### 4.3 一个被撤回的推断（重要）`[V]`

当时的第 4 条写的是"副核的判决函数算出了非法的 NextSensorMode / Vsize"。

**这个推断被撤回了。** 理由：断电重启（干净状态、未装任何探针、CAP[55]=4、L2 回 ROM）后再读同一组地址，**与故障态完全一样** ⇒ 那些值是副核镜像里的**复位默认值 / BSS 初值**，不能用来证明"副核算出了非法模式"。

> 这条教训值得单列：**"故障时读到异常值"不等于"异常值是原因"。** 必须先读一遍干净状态的基线。

## 5. 真正最接近根因的那一条：`a2 == 0`

### 5.1 断言点 `[V]`

> 环形日志第 29/30 条：`Radon ASSERT : ImageSequence::ImageSequenceParam.c` / `ASSERT : Line 1748`。
> 相机仍活着（黑屏但 PTP 正常）。

该文件串在副核数据模块里。行号 `1748` 的立即数在全代码镜像里**只出现一次**。进入该断言的唯一分支（概念级）：

```
取 ImageSequenceParam 全局对象
数组基址 == 0            → 断言"数组未初始化"
索引 > 13                → 同上
a2 == 0                  → ★ 断言 1748
a2 >= 0x10000            → 断言 0x6D5
…遍历链表…
```

⇒ **`a2` 必须落在 `1 .. 0xFFFF`。** 它的兄弟断言（`a2 >= 0x10000`）说明这是一个 **16 位寄存器值/计数**的写入校验。

### 5.2 谁在调用它 `[V]`

这个函数有 **53 个调用者，全部落在传感器读出 / SlcManager / 读出与 DMA 配置模块**，**没有一个是 ImageSequence 自己**。

⇒ 它是"**给传感器写一个 16 位值**"的统一校验器；**失败发生在某次寄存器写入时值是 0**。

### 5.3 同一次状态 dump 里的两个数 `[V]`

| 字段 | 值 |
|---|---|
| CameraMode | 0 |
| ReadOutMode | 0 |
| **LvCapMode** | **55** |
| **FrameRate** | **0** |
| DafMode / DriveMode | 2 / 0（推断） |
| Tv / AccumH / ISO / Av | 0 / −8 / 6624 / 0 |

两点结论：

1. **`LvCapMode = 55`** 证明主核确实把 cap 55 送进了共享结构（"没发 55"的担心可以排除）；
2. **`FrameRate = 0`** 是副核当前持有的帧率。若 6K RAW 本该有非 0 帧率码，这是**第一嫌疑**。

> 边界：这个 dump 与断言发生在同一次故障里，但**它们是不是同一刻、`FrameRate=0` 是不是断言的原因，都没有数据流证据**。下面那条因果是 `[I]`。

### 5.4 因果假设 `[I]`

> 读出驱动里大量 16 位值由"帧率 / VD"派生。
> 帧率 0 ⇒ 某个派生值算成 0 ⇒ 命中 `a2 == 0` 断言 ⇒ 主核永远等不到"就绪" ⇒ 黑屏 / Err70。

**依据**：`a2` 是 16 位值校验器（§5.1/5.2 均为 `[V]`）；`FrameRate=0` 是实测（`[V]`）；两者之间的"派生"关系是**推断**（`[I]`）。

**这个假设还没验证。** 验证方法很明确：找到具体写 0 的那个寄存器调用点，看它的实参来自哪个字段。**在那之前，不能写"根因已证"。**

> 另一条并列线索：主核侧的状态字检查（`0x86`）与 `a2 == 0` 是**两个不同的失败点**。它们可能同因（帧率 0 导致整条链都不可用），也可能一前一后。**目前无法判定先后。**

## 6. 目前的状态

### 6.1 没做成什么

**6K OpenGate 没有打通。** 任何"R1 已支持 6K 全高"的说法都是错的。

### 6.2 做成了什么

| # | 成果 | 等级 |
|---|---|---|
| 1 | 确认 6K RAW 的 cap 是 **55**（不是 54），SensorMode = 4 | `[V]` |
| 2 | 确认 R1 的 DS class 2 路径**被桩死**（谓词恒返回 0） ⇒ 这是"没有全高视频"的机理 | `[V]` |
| 3 | 发现副核有**独立运行时 CAP 副本**，此前所有实验都漏了它 | `[V]` |
| 4 | "在主核观测到三处一致"仍 Err70 ⇒ 排除的具体假设是**「只要把 ROM 源与运行时副本都改成 1 就能进视频档」**；这不等于"表一致性已被完全排除"（副核可见性未验） | `[V]`（观测）/ `[?]`（Xtensa 可见性） |
| 5 | 抓到断言链：通信状态字 ≠ 就绪魔数（`0x86` 分支，1469 次重试） | `[V]` |
| 6 | **定位到最像根因的断言**：`ImageSequence::ImageSequenceParam.c:1748` = `a2 == 0`，且该函数是"写 16 位寄存器值"的统一校验器 | `[V]` |
| 7 | 同 dump 里 `LvCapMode=55` / `FrameRate=0` | `[V]` |
| 8 | 撤回了一条错误推断（判决函数"算出的非法值"其实是复位默认值） | `[V]` |

### 6.3 三条候选修法 `[I]`

| 方案 | 做法 | 评价 |
|---|---|---|
| **A（推荐）** | 让 `a2` 非 0：先确认主核该发的 **FrameRate 码**是否真该是 0；若是 bug，修**主核发给副核的共享字段** | 干净，不碰副核代码 |
| B | 直接改副核的 ImageSequenceParam 对象 | 需要先读对象，且要知道"正确的值是什么" |
| C | 绕过断言（把 `beqz a2` 改成 `nop`） | **最后手段**。a2=0 之后大概率还有别的问题；且要处理副核的指令 cache |

### 6.4 恢复

**断电重启。** 所有补丁都是 RAM-only；不要指望运行时撤销（副核侧没有对应的回滚机制）。

## 7. 两个被排除的方向（省得后人再走一遍）

### 7.1 `PprchMode 0x16 / 0x17` 不是视频路径 `[V]`

一度认为这两个"固件里本来就有的 6000×4000 几何"是 OpenGate 的入口。静态查证：那个函数全固件**只有 1 个调用者**，属于 LV 显示侧的 resize 模块；它用的表**只服务 LV 的 YUV resize（显示侧）**。

⇒ 解锁它**不会**改传感器读出，**也不会**改 RAW 录制几何。

### 7.2 sm1 的时序：30p 有余量，60p 不行 `[I]`

静态**不能完全闭合**（主核没有帧周期表；副核侧也没有按帧率排的常量表），但两条量化线索指向同一方向：

- 行数比 `4160/3320` ⇒ 行率不变时 ≈ **47.9 fps**；
- 若把某个常量读作"半行 VD"（sm4→4454 行、sm1→5172 行）配套 5.56 µs 行时间 ⇒ sm1 ≈ **34.8 fps**。

真正的约束在**传感器寄存器序列**（未定位）。

⇒ 所以即使把 `a2 == 0` 修好，**6K 全高能不能跑 60p 仍然是 `[?]`**。30p 有希望，60p 大概率不行。

## 8. 方法漏洞（本轮没解决，必须写下来）

| # | 漏洞 | 后果 |
|---|---|---|
| 1 | **副核的 cache 可见性未验证** | "改运行时副本"这条路可能根本无效，也可能有效——无法区分 |
| 2 | **本线的断言链只到 1748，未到"为什么是 0"** | `a2 == 0` 的条件`[V]`，但"哪个寄存器写、为什么写成 0"没抓到；`FrameRate=0` 与它的数据流关系是 `[I]` |
| 3 | `FrameRate=0` 的**数据流未追** | 因果假设停留在 `[I]` |
| 4 | 只有 1.3.0 上测过 | 换版本结论不可直接搬 |

> ⚠️ **不要把另一条实验线的断言混进来**：上一稿在这张表里列过"曝光超时 / 累加行数 / SLCP / 缓冲满"四条候选——那是**连拍自旋线**（[05](05-burst-throttle.md) §4.4）的未知项，与 OpenGate 的 `ImageSequence…:1748` **不是同一回事**。本线的断言已经定位到 1748；撤回的是"副核判决函数算出非法模式"那条推断，**不是** 1748 本身。

---

## 9. 一句话总结

> 6K 全高打不开，**在本次这些变体里**不是"改几何就能解决"（几何、class 都改过，仍 Err70）——但**不能**说几何已被排除。
> 目前最接近根因的是一条断言：**副核在某次 16 位寄存器写入时拿到了 0**。
> 而那个 0，最可能来自主核送给它的 `FrameRate = 0`——但这条因果**还没证**。
